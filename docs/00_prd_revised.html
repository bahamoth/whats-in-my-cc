01Product Principles

제품 정의: What's in My Claude Code는 Claude Code 실행을 로컬에서 고신뢰로 관측하고, OTel-first 실행 기록(event-first)과 evidence-linked Signal을 생성해 사용자에게 제공하는 서비스다. 외부 시스템은 Pull API 또는 MCP Streamable HTTP로 읽기 중심 접근을 한다.
원칙서술
Read-only 외부 연동 no annotation외부 시스템은 Pull API와 MCP Streamable HTTP로만 접근한다. resource에 correction/label/status를 쓰는 feedback write와 webhook/callback 연동은 제공하지 않는다.
OTel-first MVP coreOTel metrics/events/traces는 1급 source layer다. trace_id/span_id와 prompt/tool/session correlation 키는 schema의 기본 필드다.
높은 수집 기본값 local_full_evidence로컬 구동과 사용자 본인 insight 목적이므로 높은 수집 수준을 기본으로 한다. secret protection이 선행된다.
Event-first 구성 ObservedEvent뷰와 상관관계는 별도 중간 레이어 없이 ObservedEvent + correlation 키(tool_use_id · request_id · turn_id · message_id)로 직접 구성된다.
Deterministic insight L1 Signalinsight는 deterministic L1 detector 5종(tool_failure, risky_action, context_bloat, final_state_mismatch, re_read)이 생성하는 Signal이다. 비결정·비로컬 LLM 판정 경로는 두지 않으며, evidence_refs 없는 Signal은 존재할 수 없다.
집계 정직성 F1 · count only지표는 합성 가능한 count만 제공하고 rate scalar는 제공하지 않는다 — 비율은 소비자가 계산한다.

설계 결정·변경 이력의 SSOT는 git history와 implementation-notes.html이다. 이 문서는 현재 시스템만 서술한다.

02Product Definition

What's in My Claude Code는 Claude Code 실행 중 발생하는 transcript, OpenTelemetry, hook lifecycle, file/git state, verification run을 수집·정규화·연결하여 사용자가 실행 흐름과 문제 원인을 이해할 수 있도록 돕는 로컬 서비스다.

제품의 핵심 산출물은 개선 패치가 아니라 evidence-linked insight resource(Signal + 온디맨드 SessionMetrics)다. 사용자는 UI에서 event-first replay(대화 스트림 · per-event 디테일 패널 · Raw 탭), insight strip, 분석 패널(세션 지표 · detector 분포)을 확인한다. 외부 도구는 Pull API 또는 MCP Streamable HTTP로 동일한 resource를 읽는다.

03Goals and Non-goals

Goals

  • Claude Code 실행을 correlation 키로 연결된 event-first 실행 기록으로 설명한다.
  • OTel metrics/events/traces를 1급 source layer로 다룬다.
  • 파일 변경과 검증 run의 연결을 보여준다.
  • source별 raw evidence와 normalized ObservedEvent를 모두 제공한다.
  • 사용자에게 tool failure, risky action, context bloat, final-state mismatch, re-read 등의 deterministic Signal과 온디맨드 SessionMetrics를 제공한다.
  • Pull API와 MCP Streamable HTTP로 읽기 중심 resource access를 제공한다.

Non-goals

  • Claude Code 설정, hook, command, skill, memory를 수정하지 않는다.
  • 개선 patch나 설치 스크립트를 생성하지 않는다.
  • 외부 시스템이 signal/resource에 correction이나 label을 쓰는 기능을 제공하지 않는다.
  • hidden reasoning 또는 private chain-of-thought를 복원한다고 주장하지 않는다.
  • 원격 multi-user SaaS 운영 요구사항을 MVP 범위로 두지 않는다.

06Requirement Catalog

Observation

OBS-1Transcript CaptureCore
Requirement
Claude Code transcript/JSONL에서 user message, assistant message, tool call, tool result, large output reference를 수집한다.
Acceptance
알 수 없는 필드는 raw payload에 보존하고 normalized event와 source offset을 연결한다.
OBS-2OTel Signal CaptureCore
Requirement
metrics, logs/events, traces를 모두 수집 가능한 1급 source layer로 정의한다.
Acceptance
trace/span hierarchy와 prompt/tool/session correlation key가 data model의 optional add-on이 아니라 기본 field로 존재한다.
OBS-3Hook Lifecycle ObservationCore
Requirement
hook 실행 결과(hook_success / hook_additional_context / hook_system_message / hook_cancelled 등)를 transcript live tail에서 hook_event로 관측한다 — hook 결과가 transcript attachment로 기록되므로 별도 collector 없이 수집된다. (전용 POST /hooks/v1/events collector는 2026-06 제거: 단일 사용자 범위에서 transcript와 중복이고 순증분이 git 이력으로 대체 가능 — implementation-notes 참고.)
Acceptance
transcript의 hook 결과 attachment를 hook_event로 정규화하고 source offset과 연결한다. 누락은 누락으로 노출한다.
OBS-4File/Git State ObservationCore
Requirement
read/write/edit, diff hunk, pre/post snapshot, branch, commit, dirty state, verification command result를 관측한다.
Acceptance
특정 diff hunk에서 prompt, tool call, verification run으로 역추적 가능해야 한다.

Correlation and Insight

NOR-1Source-preserving NormalizationCore
Requirement
모든 raw source event를 ObservedEvent로 변환하되 source payload reference를 유지한다.
Acceptance
각 ObservedEvent에서 원본 transcript, OTel span/log, hook event, file event로 jump 가능해야 한다(/v1/events/:event_id/raw).
COR-1Deterministic CorrelationCore
Requirement
tool_use_id, request_id, turn_id, message_id를 ObservedEvent의 1급 correlation 키 컬럼으로 유지하고, trace_id/span_id·file_path와 함께 event 간 연결에 사용한다.
Acceptance
동일 tool call이 transcript, OTel, hook에 중복으로 보이면 correlation 키로 묶어 하나의 실행 단위로 조회·렌더할 수 있다(span dedup 포함). 사전 병합된 중간 표현은 저장하지 않는다 — 뷰가 event를 직접 그린다.
COR-2Deterministic Outcome ResolutionCore
Requirement
tool 실행 outcome을 결정적 우선순위 체인(① OTLP tool_result log ② hook post_tool_use exit_code ③ transcript "Exit code N" / <tool_use_error> 래퍼 ④ Unknown)으로 판정하고, 하니스 마커 기반 disposition(user_rejected / policy_denied / cancelled / backgrounded)을 분류한다.
Acceptance
판정 결과는 status_provenance(measured / estimated / unknown)로 구분되어 추정과 측정을 섞지 않는다.
INS-1Evidence-linked SignalsCore
Requirement
deterministic L1 detector 5종(tool_failure, risky_action, context_bloat, final_state_mismatch, re_read)이 Signal을 생성한다. detector manifest는 /v1/detectors와 MCP list_detectors로 공개한다.
Acceptance
evidence_refs가 없는 Signal은 저장·표시할 수 없다. 모든 Signal은 provenance(detector, version "L1", rule_pack)를 가진다.
INS-2On-demand Session MetricsCore
Requirement
세션 지표(SessionMetrics)는 저장하지 않고 조회 시 on-demand로 계산한다: tool_call_total, tool_failure_count, verification_total/passed/failed/unknown, context_bloat_count, disposition별 count, detector_firing.
Acceptance
rate scalar는 제공하지 않는다 — 합성 가능한 count만 반환하고 비율은 소비자가 계산한다(F1 집계 정직성).

Serving

SRV-1Local UICore
Requirement
event-first replay(대화 스트림 · per-event 디테일 패널 · Raw 탭), insight strip(컨텍스트 효율/토큰/검증/도구 실패/비용 카드 + provenance 배지), 분석 패널(세션 지표 · detector 분포)을 제공한다.
Acceptance
사용자는 한 세션에서 signal, 근거(evidence_refs), 지표, raw source를 끊기지 않고 탐색할 수 있다.
SRV-2Pull APICore
Requirement
외부 도구가 session, events, signals, metrics, fingerprint(세션 환경 — 모델·CC버전·branch·instruction 해시), cross-session metrics series(/v1/metrics), usage(+ cross-session baseline), diff-hunks, verification-runs, detectors, raw event를 GET 중심 read-only API로 조회한다(/v1/*, SSE /v1/stream 포함).
Acceptance
API는 domain schema를 반환하고 UI 렌더링 구조에 의존하지 않는다. 응답은 {meta:{schema_version, collection_profile, generated_at,…}, data} 래핑을 유지한다.
SRV-3MCP Streamable HTTPCore
Requirement
로컬 MCP endpoint(/mcp)를 통해 read-only tools 9종을 제공한다: search_sessions · get_file_lineage · get_otel_trace · get_session_turns · list_detectors · get_project_metrics · get_session_metrics · get_session_signals · get_session_fingerprint.
Acceptance
endpoint는 localhost binding을 기본으로 두고, local auth token은 --auth on일 때 적용된다(기본 off — 단일 사용자 dev).
