00Overview

이 문서는 docs/superpowers/specs/2026-05-19-witmcc-slice1-transcript-design.md 및 docs/superpowers/plans/2026-05-19-witmcc-slice1-transcript.md 대비 실제 구현의 차이를 기록한다. CLAUDE.md 지침에 따라 설계 결정, 편차, 트레이드오프, 열린 질문을 모두 포함한다.

전체 상태: slice-1 완료. 22개 테스트 통과. Pull API 4 endpoint 정상 동작.

아래 각 항목은 의도적 편차(Intentional Deviation)로 분류하며, 사양 위반이 아닌 구현 과정에서 내린 유효한 해석 또는 확장이다.

01Intentional Deviations

DEV-01 Rust toolchain: 1.78 → 1.88 toolchain

사양 원문: plan의 Cargo.toml bootstrap에서 MSRV 1.78로 명시.

실제 구현: Cargo.toml의 rust-version = "1.88". axum / sqlx 등 transitive dependency가 1.78로 컴파일되지 않아 최신 stable(1.88)로 상향.

영향: 로컬 개발 환경 요구사항 상승. 1.78 환경에서는 빌드 불가.

관련 커밋: 2288329

DEV-02 cli.bind 타입: String → std::net::IpAddr cli

사양 원문: bind를 문자열로 처리.

실제 구현: clap 인수 파싱 단계에서 IpAddr로 직접 파싱하여 잘못된 IP 주소 입력을 CLI 레벨에서 즉시 거부한다.

트레이드오프: 검증이 런타임보다 이르게 발생. hostname 형식은 허용하지 않음. loopback enforcement가 is_loopback() 체크로 단순화됨.

관련 커밋: 944ca53

DEV-03 loopback 범위: 127.0.0.1 단일 → is_loopback() (127.0.0.0/8 + ::1) serve

사양 원문: 127.0.0.1 엄격 바인딩 명시.

실제 구현: IpAddr::is_loopback()을 사용하므로 127.x.x.x 전체 및 IPv6 ::1도 허용.

보안 영향: 127.0.0.0/8 전체는 모두 loopback이므로 실제 LAN/WAN 노출 없음. 일반 HTTP/1.1 브라우저 트래픽 기준으로는 동등.

관련 커밋: 944ca53

DEV-04 tool_call_to_result 엣지: dangling-only → matched self-loop 추가 graph

사양/plan 원문: dangling tool_result에 대해서만 tool_call_to_result 엣지를 emit한다.

실제 구현: matched call (tool_result payload가 tool_call 노드에 병합된 경우)도 self-loop 엣지를 emit하되 attributes.merged = true를 설정한다. (from == to == tool_call node id)

이유: graph 소비자가 결과 존재 여부를 엣지로 쿼리할 수 있어야 하며, 단순 노드 payload lookup보다 그래프 traversal이 일관됨. 결정론 테스트에서 이 동작을 검증.

관련 커밋: 2673333, 5fdc9ff

DEV-05 by_event_uuid 병합 후 result UUID 재매핑 graph

사양 원문: 명시 없음 (구현 세부사항).

실제 구현: graph::compute에서 tool_result payload를 tool_call 노드에 병합한 뒤, by_event_uuid[result_uuid]를 surviving call 노드를 가리키도록 갱신한다.

이유: message_reply 엣지가 result uuid를 참조할 때 dangling edge가 되는 것을 방지. UUID 재매핑 없이는 "sidechain" 시나리오 테스트가 실패함.

관련 커밋: 2673333, 5fdc9ff

DEV-06 host_allowlist 미들웨어: Host 헤더 부재 시 uri.authority() fallback api

사양 원문: Host 헤더 기반 allowlist 검사 명시.

실제 구현: Host 헤더가 없으면 uri.authority()를 대신 사용해 allowlist를 검사한다. 헤더도 authority도 없으면 통과.

이유: axum-test의 in-process HTTP 테스트 클라이언트가 Host 헤더를 포함하지 않음. 실제 HTTP/1.1 브라우저는 항상 Host를 전송하므로 프로덕션 보안 등가.

관련 커밋: cd6398f

DEV-07 FileHistorySnapshotRecord: sessionId 미파싱 ingest

사양 원문: 모든 JSONL record 타입에서 session_id 추출 기대.

실제 구현: 실제 JSONL file-history-snapshot 레코드에 sessionId 필드가 없음. 파싱 시 빈 session_id로 저장되며 세션 범위 쿼리에서 제외됨.

영향: file-history-snapshot ObservedEvent는 DB에 저장되지만 /v1/sessions/{id} 응답에 포함되지 않음.

후속 작업: 인접 레코드의 session_id를 역방향으로 전파하는 로직이 필요 (future slice).

관련 커밋: 38b6439, b077ca5

02Known Gaps / Follow-ups

아래 항목은 사양에서 정의되었으나 slice-1 범위에서 구현되지 않은 기능 및 추후 슬라이스에서 해결해야 할 사항이다.
  • No live tail / file watcher. ingest를 재실행해야 새 JSONL 라인을 수집한다. 멱등(idempotent).
  • No redaction. --all 인제스트는 raw JSONL에서 secrets를 그대로 수집할 수 있다. 사용 전 주의 필요.
  • Pagination hard limit only. next_cursor는 항상 null. 커서 기반 페이지네이션 미구현.
  • No MCP server. MCP Streamable HTTP endpoint는 later slice.
  • No UI. causal replay, why panel, finding 등 UX는 later slice.
  • No findings engine. Finding / RootCauseHypothesis / QualitySummary 생성 미구현.
  • SystemRecord fixture 없음. 실제 JSONL에 type=system 레코드 2건이 존재하나 테스트 fixture 미포함.
  • _sqlx_migrations bin version 검증 미구현. serve 명령은 observed_event 테이블 존재 여부만 확인하고 migration 버전을 검증하지 않는다.
  • OTel / Hook / File-Git 수집기 없음. transcript JSONL만 지원. 나머지 source layer는 later slice.

05Slice-2 Intentional Deviations

DEV-S2-01 event_id lookup key instead of event_uuid api

사양 원문: event_uuid를 raw record lookup key로 명시.

실제 구현: observed_event PK인 event_id (ULID)를 사용. 일부 레코드 타입(file-history-snapshot)은 event_uuid를 포함하지 않아 event_uuid만으로는 모든 이벤트를 식별할 수 없음. 클라이언트는 graph_node.source_event_ids[0]를 사용해 event_id를 참조한다.

영향: API path는 /v1/events/:event_id/raw. 기존 event_uuid 기반 참조가 있다면 event_id로 전환 필요.

DEV-S2-02 SPA fallback returns 200 for unknown routes serve

사양 원문: 명시 없음 (SPA routing 세부사항).

실제 구현: axum .fallback(spa_handler)는 non-asset path에 대해 index.html을 status 200으로 반환한다. SPA의 * 라우트가 클라이언트 측에서 "not found"를 표시한다.

이유: deep-link refresh가 정상 동작해야 하므로 의도적. /random-path로 접근해도 200이 반환되며 SPA가 라우팅을 처리한다.

DEV-S2-03 webui/dist/ is build-required, not committed toolchain

사양 원문: 명시 없음 (빌드 아티팩트 관리 세부사항).

실제 구현: webui/dist/는 완전히 gitignore 처리됨. README 및 justfile에서 just webui-build를 cargo build 전에 실행하도록 안내. build.rs 자동화를 통한 통합은 cargo-only 소비자에게 Node 툴체인을 강제하게 되므로 채택하지 않음.

트레이드오프: 빌드 단계가 명시적이고 분리됨. rust-embed가 dist 파일을 컴파일 시점에 포함하므로 webui-build 없이 cargo build하면 embedded SPA가 없는 바이너리가 생성됨 (static_serve 테스트 실패 포함).

DEV-S2-04 Lane mapping is client-side webui

사양 원문: 명시 없음 (lane 분류 책임 소재).

실제 구현: node_kind → lane 매핑은 TypeScript 상수 (webui/src/api/laneMapping.ts)에 정의됨. 서버 응답에는 포함되지 않음.

트레이드오프: 새로운 node_kind가 추가되면 webui 변경이 필요하지만, 서버 응답 스키마는 안정적으로 유지됨. 서버 사이드 lane 매핑은 API 계약 변경 없이 클라이언트 독립적 진화를 방해함.

DEV-S2-05 source.kind passes raw DB value api

사양 원문: source.kind를 정규화된 값(예: "transcript")으로 반환.

실제 구현: endpoint는 raw raw_event.source_type 값 ("claude_transcript")을 그대로 반환함. ingest layer의 식별자와 직접 추적 가능하며 정규화 레이어 없이 provenance를 보존함.

영향: 클라이언트가 "transcript"가 아닌 "claude_transcript"를 기대해야 함. 추후 정규화 레이어 추가 시 breaking change 가능.

08Slice-3 Intentional Deviations

DEV-S3-01 OTLP/JSON only (no protobuf) api

OTLP/HTTP은 protobuf와 JSON 둘 다 지원하지만 slice-3는 JSON만 받는다. SDK 측에서 OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/json 설정 필요.

DEV-S3-02 Traces only — no metrics/logs api

metrics는 time-series 모델이라 ObservedEvent에 직접 매핑되지 않고, logs는 traces가 가진 인과 정보 없이 양만 늘린다. 두 signal은 후속 슬라이스.

DEV-S3-03 Telemetry facet stored inside payload JSON model

DB schema 변경 회피를 위해 facet은 payload.telemetry 키 아래 포함된다. trace_id/span_id/parent_span_id/ latency_ms는 top-level 컬럼 사용 — 인덱스 가능.

DEV-S3-04 No transcript ↔ OTel merge in slice-3 graph

Transcript producer가 아직 trace_id를 emit하지 않으므로 merge가 자동 발생하지 않는다. graph_node의 merge_keys에 trace_id+span_id는 깔려 있어 producer 추가 시 자동 동작.

DEV-S3-05 No span_parent edges; otel_span nodes excluded from turn_order graph

parent_span_id는 column에 저장되지만 span_parent edge kind는 아직 emit하지 않는다. turn_order edge는 conversation turn 의미라 otel_span 노드는 명시적으로 필터한다. 데이터 경로 우선 검증 후 후속 슬라이스에서 cross-kind correlation을 추가.

DEV-S3-06 list_sessions filters out empty session_id api

OTel span이 session.id attribute 없이 들어오면 DB에 빈 문자열로 저장된다. GET /v1/sessions는 WHERE session_id != ''로 이런 행을 응답에서 제외 — spec §6.3 에 정의된 동작.

DEV-S3-07 otel::store: rebuild graph on every POST, including duplicate-raw POSTs graph

사양 원문: 명시 없음 (graph staging policy 세부사항).

최초 구현 (post-merge에서 발견된 갭): otel::store는 observed_event 행만 삽입하고 rebuild_session을 호출하지 않았다. 결과적으로 HTTP 경로(POST /otel/v1/traces)에서 ingest 직후 GET /v1/sessions/:id/graph가 404를 반환했다. 테스트는 build::rebuild_session을 명시 호출해서 통과했기에 회귀 검출이 안 됐다. fix는 store 내부에서 touched 세션마다 자동 rebuild를 호출 (커밋 21527b9).

두 번째 갭 (self-heal): raw dedup이 발동하면 continue로 루프를 빠져 나가 touched에 session_id가 들어가지 않는다 → rebuild도 skip. 결과적으로 이전 버그 바이너리가 만든 stale state(observed_event row 있음, graph_node 없음)는 새 바이너리에서 같은 fixture를 재POST해도 자가복구되지 않는다. fix는 touched.insert를 dedup 체크보다 먼저 실행 (커밋 78b2f30).

채택한 정책: "ingest event는 항상 affected session의 graph rebuild를 유발한다. raw row 중복 여부와 무관." graph_node는 observed_event로부터 결정론적으로 파생되는 view이므로 DELETE + 재INSERT는 idempotent. 데이터(raw_event, observed_event)는 절대 교체되지 않는다 — graph view만 source-of-truth 기준으로 다시 빌드된다.

트레이드오프:

  • 장점: self-heal (바이너리 업그레이드/crash 후 재POST로 복구), end-state idempotency, 단일 세션 rebuild 비용은 SQLite 로컬에서 sub-ms.
  • 단점: 고volume retry 환경(예: OTel SDK가 같은 batch를 초당 수십 번 쏘는 시나리오)에서 데이터 변화 없는 rebuild가 누적될 수 있음. slice-3 단일 사용자 scale에선 무시 가능.

재검토 트리거: 다음 중 하나라도 발생하면 정책 변경 후보:

  • 고volume OTel ingestion (retry 폭주 패턴 관측)
  • multi-source ingest 추가(Hook/File-Git)로 session-level rebuild 비용 증가
  • graph_node에 idempotent하지 않은 side-effect 추가(예: ext index, notification)

대안 옵션 (현재 미채택):

  • Option D — recovery-only rebuild: if !inserted && graph_node_count(session) == 0 { rebuild }. duplicate인데 graph가 이미 있으면 skip. 단점: stale graph가 일부만 비어 있는 경우 감지 불가.
  • Option E — dirty flag: 세션별 graph_dirty 비트. 새 observed_event 삽입 시 set, rebuild 후 clear. 시작 시 dirty 세션 스캔. 가장 정교하지만 추가 schema + lifecycle 필요.

관련 커밋: 21527b9 (initial fix), 78b2f30 (self-heal extension).

11Slice-4 Intentional Deviations

DEV-S4-01 External hook vs transcript-internal hook merge_keys split via parser_version graph

사양 원문: 명시 없음 (graph merge_keys 세부사항).

실제 구현: graph::build::compute의 EventKind::HookEvent branch가 e.parser_version.starts_with("hook@")로 분기한다. 외부 hook (slice-4)은 (session_id, hook_event_name, tool_use_id)로 merge하고, transcript-내부 hook attachment (slice-1)는 기존 event_uuid merge_keys를 유지한다.

이유: 두 source의 식별 키가 본질적으로 다르다. 외부 hook은 hook_event_name + tool_use_id로 의미적 동일성을 가지지만 event_uuid는 없다. 반대로 transcript-내부 hook은 부모 message의 event_uuid로만 식별 가능. 둘을 같은 merge_keys 스키마로 강제하면 한 쪽이 항상 dangling이 된다.

후속: tool_use_id 기반 cross-source dedup은 별도 slice. 현재는 외부/내부가 별도 노드로 공존한다.

DEV-S4-02 Pass-through body shape (no wrapper envelope) api

사양 원문: 명시 없음.

실제 구현: Claude Code의 stdin JSON을 그대로 받는다. wrapping object ({"events": [...]}) 없이 단일 hook object 또는 JSON array 직접. 전체 JSON 본문이 그대로 raw_event.payload에 저장됨.

이유: 사용자 forward script가 cat | curl --data-binary @-로 단순해진다. wrapping을 추가하면 user-side script가 jq 등으로 변환해야 하며, 그 변환은 hook 페이로드 보존성을 해친다.

DEV-S4-03 1 MB body limit (vs OTel's 4 MB) api

실제 구현: MAX_HOOK_BODY = 1 * 1024 * 1024. OTel receiver는 4 MB.

이유: 단일 hook event는 대부분 수 KB. 1 MB는 batch 50~100건 수준이며 hook의 high-frequency 특성과 fail-soft 요구를 고려하면 적절. OTel은 batch span 수가 더 많아 4 MB가 필요했음.

DEV-S4-04 Forward script not auto-installed ops

사양 원문: CLAUDE.md 명시적 non-goal — "Claude Code 설정 / hook / command / skill / memory 변경".

실제 구현: README에 forward script 예제와 settings.json 스니펫만 제공. witmcc init-hooks 같은 자동 설치 서브커맨드는 없음.

이유: Claude Code 설정에 대한 write는 product principle 위반. 사용자가 명시적으로 hook을 등록해야 데이터가 들어온다.

DEV-S4-05 Hook ↔ transcript-internal hook 중복 미해결 (known gap) model

현황: Claude Code가 PreToolUse hook을 트리거하면 외부 hook (이 slice의 forward script로 들어옴)과 transcript-내부 hook attachment 두 경로로 동일 사건이 기록될 수 있다. graph_node는 각각 별도 노드로 보존된다.

이유: transcript-내부 hook attachment는 hook_event_name을 명시적으로 carry하지 않으며, 외부 hook은 event_uuid를 갖지 않는다. cross-source dedup은 시간 윈도우 + tool_use_id 휴리스틱이 필요하며 별도 slice.

영향: tool 사용 횟수가 두 source 모두 활성일 때 부풀려 보일 수 있음. by_kind.hook_event count 해석 시 주의.

DEV-S4-06 No DDL migration (raw_event/observed_event schema 그대로 재사용) db

사양 원문: 명시 없음.

실제 구현: migration 추가 없음. source_type이 TEXT column이라 "hook" 값 추가에 schema 변경 불필요. 기존 OTel slice의 0002_telemetry.sql 인덱스도 그대로 적용된다.

후속: hook 전용 인덱스 (source_type='hook', session_id) 는 hook-only 세션이 큰 규모로 증가할 때 추가 검토.

14Slice-5 Intentional Deviations

DEV-S5-01 Synthetic session_id = "filesystem" model

사양 원문: spec §4 (CLI Surface) — file/git 이벤트는 Claude Code session에 자동 귀속되지 않으며, 합성 well-known id "filesystem"로 emit한다고 명시.

실제 구현: FILESYSTEM_SESSION_ID 상수. 모든 store_file_event / store_commit가 이 id를 사용. GET /v1/sessions에 일반 세션처럼 표시되며, /v1/sessions/filesystem/graph로 file_event / git_commit / diff_hunk 노드를 보여준다.

후속: 시간 윈도우 + cwd overlap 휴리스틱으로 실제 Claude session에 re-key 하는 작업은 별도 slice.

DEV-S5-02 Git poller startup: HEAD 이전 commit replay 생략 collector

사양 원문: spec §9.3 — "on startup, replay any commits since the last git_commit row in DB".

실제 구현: run_git_poller 시작 시 last_seen = HEAD OID로 초기화. DB의 마지막 git_commit row를 조회하지 않는다. 이후 tick부터 새 commit만 ingest.

이유: 큰 repo에서 처음 시작 시 수십만 commit replay는 startup 비용이 과도하다. dedup으로 무결성은 보장되나 시간이 길어진다. slice-5 범위에서는 startup 이후 새 commit observability가 핵심 가치이며, 과거 commit ingest는 별도 backfill 서브커맨드로 분리 가능.

영향: serve 재시작 사이의 commit은 놓칠 수 있음. watcher와 poller가 항상 떠 있는 사용 패턴이면 무관.

DEV-S5-03 git2 객체는 spawn_blocking으로 격리 runtime

현황: git2::Repository와 그 파생 객체 (Commit, Revwalk, Patch)는 raw FFI pointer를 보유하며 !Send다. tokio::spawn future 안에서 직접 사용하면 컴파일 에러.

실제 구현: git_poller::extract_new가 모든 git2 작업을 동기 함수로 캡슐화한 뒤 tokio::task::spawn_blocking로 실행. 추출된 Vec<(CommitRecord, Vec<HunkRecord>)>는 plain data여서 await 가능.

DEV-S5-04 Deterministic diff_hunk_id = "hunk_{sha}_{idx}" id

사양 원문: §5.7 hunk payload에 ULID 권고.

실제 구현: commit SHA + 추출 순서 index로 deterministic id 생성. 동일 commit을 두 번 ingest하면 같은 id이므로 diff_hunk 테이블의 PRIMARY KEY로 dedup되고 canonical-JSON sha256으로 raw_event dedup된다.

이유: ULID 사용 시 동일 commit re-ingest가 새 행을 만든다 (raw dedup은 막지만 diff_hunk 테이블은 별도 ID). Deterministic id면 두 단계 모두 idempotent.

DEV-S5-05 250 ms in-memory debounce (no notify-debouncer-full) collector

사양 원문: §8 — "250 ms debounce coalesces them".

실제 구현: HashMap<(PathBuf, FileChange), Instant> + 100 ms ticker. Editor의 unlink+create+chmod 시퀀스가 단일 file_event 한 건으로 flush됨.

후속: 부하 환경에서 이벤트 누락이 관측되면 notify-debouncer-full로 교체. 슬라이스 5 범위에서는 수동 dependency 최소화.

DEV-S5-06 vendored-libgit2 기본 활성화 build

실제 구현: Cargo.toml에서 git2 = { version = "0.19", default-features = false, features = ["vendored-libgit2"] }. 시스템 libgit2 의존성 없이 cargo build만으로 빌드 성공.

트레이드오프: 빌드 시간이 처음에 한 번 늘어남 (~30 s), 결과 바이너리 크기 +1 MB. 대신 호스트 OS 호환성 문제 제거.

DEV-S5-07 Patch preview 4 KB 절단, hunk 2000건 cap storage

사양 원문: §5.7 — "truncated to 4 KB", §8 — "MAX_HUNKS_PER_COMMIT = 2000".

실제 구현: truncate_patch_preview는 UTF-8 char boundary에서 자르고 "\n…[truncated]" 추가. store_commit은 입력 hunk가 cap을 초과하면 잉여를 CommitIngestResult::dropped_hunks_over_limit로 카운트.

후속: 큰 commit이 자주 발생하는 환경이면 cap을 config로 노출 검토.

DEV-S5-08 Files lane 위치: State와 Hook 사이 (5번째) ui

사양 원문: §7.1 — Files lane을 State와 Hook 사이에 배치.

실제 구현: LANES = ['Intent','Context','Action','State','Files','Hook','OTel','Quality'] 총 8 lane. laneForNodeKind가 file_event / git_commit / diff_hunk를 모두 'Files'로 매핑.

DEV-S5-09 Lineage edges (mutates, verifies) 보류 graph

사양 원문: §2 (Out of Scope) — slice-5는 노드만 만들고 tool_call → file_event 등 lineage edge는 후속 slice.

실제 구현: graph::build::compute는 file/git 세 EventKind에 대해 노드만 생성하고 turn_order edge에서도 제외한다 (대화 turn이 아니므로). 새 edge_kind은 추가하지 않음.

DEV-S6-01 Two-stage receiver instead of a separate capture tool

맥락: 초기 작업 계획에서 "fixture 동결용 1회 dump script"를 별도 도구로 두려 했으나, CLAUDE.md의 source-preserving 원칙에 따르면 raw payload 보존은 모든 receiver의 영구 동작이다. 별도 도구는 컨셉을 흐림.

구현: Stage 1 receiver는 OTLP/JSON 본문을 그대로 raw_event에 넣는 minimal endpoint다. Stage 2 normalize는 그 위에 점진 적층. 실 Claude Code 캡처는 Stage 1 머지 직후 사용자가 실 claude를 한 번 띄워서 DB에 들어온 row를 scripts/freeze_real_otel_fixtures.py로 추출 + redaction.

DEV-S6-02 source_type "otel" vs label "otel-traces"

DEV-S6-03 Per-data-point ObservedEvent (no rollups)

맥락: metric은 시계열이라 rollup하는 게 자연스러워 보이지만 evidence-linked finding의 단위는 single sample이다.

구현: resourceMetrics[].scopeMetrics[].metrics[].dataPoints[]의 각 datapoint = 한 ObservedEvent + 한 graph_node. Claude Code의 기본 export interval (60s)로 bounded되므로 row 폭발은 없다 (10 instruments × 12 sessions/day ≈ 17 k rows/day).

DEV-S6-04 event_id에 attribute hash 포함

맥락: 실 Claude Code의 metric 한 instrument는 같은 timestamp에 다른 attribute set으로 여러 datapoint를 보낼 수 있다 (이번 v01 fixture는 매 instrument에 2 dataPoint). spec §5.5의 초기 event_id 공식 metric:<resource>:<instrument>:<time>:<attr>은 이미 attr_sha8을 포함하지만 graph merge_keys에는 누락 → 6 datapoint가 3 node로 dedup됨.

구현: graph::build::compute의 metric_sample / log_record merge_keys에 event_id 자체를 추가. 같은 (instrument, time)이라도 attribute가 다른 datapoint는 별도 노드.

DEV-S6-05 row_to_observed의 신규 EventKind 매핑 누락 (수정됨)

증상: 첫 Stage 2 실행 시 observed_event는 6 row 들어가지만 graph_node는 0. 원인은 repo_observed::row_to_observed의 match kind.as_str()에 "metric_sample" / "log_record" 분기 누락 — DB 행이 EventKind::Unknown로 역직렬화되고 graph compute가 _ => continue로 skip.

교훈: 새 EventKind 추가 시 loader도 반드시 동시에 갱신한다. 후속 slice에선 EventKind enum/match를 strum 등으로 derive해서 동기화 비용을 없앨 만함.

DEV-S6-06 cross-source dedup (otel-logs ↔ transcript) 보류

맥락: 실 fixture에서 event.name="hook_execution_complete" log record가 등장 — 같은 사건이 slice-4 hook receiver로도 들어올 수 있다. 두 source가 모두 활성이면 같은 hook 실행이 두 노드로 보일 가능성.

구현: 본 slice에서는 별도 노드로 보존. dedup은 시간 윈도우 + attribute heuristic이 필요하며 별도 slice (DEV-S4-05와 같은 패턴).

DEV-S6-07 raw_event index에 session_id 포함하지 않음

사양 원문: design spec §5.3 — idx_raw_source_type_session ON raw_event(source_type, session_id).

실제 구현: raw_event 테이블에 session_id 컬럼이 없다 (session 귀속은 observed_event에만 있음). migration 0004의 인덱스를 idx_raw_source_type ON raw_event(source_type) 단일 컬럼으로 변경. /v1/health/sources는 source_type GROUP BY만 하므로 단일 컬럼 인덱스로 충분.

DEV-S6-08 doctor는 환경변수 셸 process만 본다

맥락: 사용자가 ~/.claude/settings.json의 env 객체에 OTel 변수를 설정해도 doctor 실행 셸에는 적용 안 됨. Claude Code는 자기 child process에만 그 env를 주입한다.

DEV-S6-10 doctor의 settings.json 자동 변경 없음 (CLAUDE.md 원칙 재확인)

20Slice-7 Intentional Deviations

DEV-S7-01 Cursor strategy: rehash whole file instead of byte-offset map

사양 원문: design spec §6.1 proposed an in-memory HashMap<PathBuf, u64 byte_offset> seeded from raw_event on startup.

구현: transcript_tail::run re-calls ingest::store::ingest_file(pool, path) on every debounced flush. The existing UNIQUE(source_uri, source_line_no, payload_sha256) constraint absorbs duplicates so no cursor state is needed.

트레이드오프: every flush rehashes the whole file (slice-1 stream_file reads the entire JSONL again, computes per-line sha256). Bounded by Claude Code's per-session JSONL size (typically MB-scale; bahamoth's largest at smoke time was a few MB). In exchange: zero cursor state to corrupt, no migration, and the live tail shares its entire codepath with ingest --all so any slice-1 bugfix benefits both.

후속: byte-offset cursor is a future optimisation if/when users report large transcripts hot-spotting the watcher.

DEV-S7-02 Initial catch-up scan runs in a background task

증상: first impl awaited the catch-up scan inline, which made witmcc serve startup time = total transcript bytes / parse rate. CI test serve_accepts_watch_and_poll_flags (8s budget) failed because the test host's real ~/.claude/projects contained too many MB to scan in time.

구현: scan_initial is spawned into a dedicated tokio task wrapped in tokio::select! on cancel.cancelled(). Serve startup is now instantaneous; the notify watcher picks up live writes regardless of whether catch-up is still running. UNIQUE constraint absorbs any race.

DEV-S7-03 Transcript tail is on by default

맥락: the whole slice exists because the user wanted "한번에" — making the tail opt-in would have defeated the goal.

구현: default-on; opt-out via --no-watch-transcripts. Two existing tests (tests/cli_serve.rs::serve_accepts_watch_and_poll_flags and tests/doctor.rs::spawn_server) pass the opt-out so they do not depend on the test host's real transcripts root state.

DEV-S7-04 Recommendations now consult effective_env, not process env

증상: v0.1 build_recommendations only looked at report.envs (process env), so users who had OTel keys in ~/.claude/settings.json's env block (which is the documented way to configure Claude Code) got a misleading "Set the following…" recommendation.

구현: v0.2 uses report.effective_env (settings hierarchy merge) OR process env. Only keys missing from both are recommended. The endpoint suffix rule (/otel) is checked against both sources too. Verified on bahamoth's env — recommendation block now correctly omits the OTel keys he already has.

DEV-S7-05 Project walk stops at .git even without .claude/

맥락: a project may have no .claude/ dir yet, but the user still expects doctor to report "project shared: absent at <repo>/.claude/settings.json" rather than walk up to $HOME.

구현: project_paths stops at the first of: (a) directory containing .claude/, (b) directory containing .git/. In case (b) the returned paths point into the not-yet-existing .claude/ dir so doctor renders them as ∅ at the correct location.

DEV-S7-06 Plugin scope label = plugin:<dirname>

구현: plugin manifests appear with scope label plugin:my-plugin rather than just plugin, so users with multiple plugins can tell which one contributed which hook. For tests, WITMCC_DOCTOR_PLUGINS_ROOT env overrides the default ~/.claude/plugins location so the test harness doesn't touch the host's real plugins dir.

DEV-S7-07 Hook entry parser accepts two shapes

맥락: Claude Code docs show hooks.<Event>[].hooks[].command (nested), but some examples in the wild use hooks.<Event>[].command (flat).

구현: collect_hooks_into tries the nested form first, then falls back to flat. Both yield a HookEntry; substring match on "hooks/v1/events" stays the same.

DEV-S7-08 docs/02 + docs/03 HTML patch still deferred

Same rationale as DEV-S6-09. design spec + implementation-notes (this page) carry the load. Adding a "doctor" or "live tail" entry to docs/02's pipeline diagram requires editing a single-line HTML; deferred to a docs-only slice.
