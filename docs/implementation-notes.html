아래 각 항목은 의도적 편차(Intentional Deviation)로 분류하며, 사양 위반이 아닌 구현 과정에서 내린 유효한 해석 또는 확장이다.

01Intentional Deviations

DEV-01 Rust toolchain: 1.78 → 1.88 toolchain

사양 원문: plan의 Cargo.toml bootstrap에서 MSRV 1.78로 명시.

실제 구현: Cargo.toml의 rust-version = "1.88". axum / sqlx 등 transitive dependency가 1.78로 컴파일되지 않아 최신 stable(1.88)로 상향.

영향: 로컬 개발 환경 요구사항 상승. 1.78 환경에서는 빌드 불가.

관련 커밋: 2288329

DEV-02 cli.bind 타입: String → std::net::IpAddr cli

사양 원문: bind를 문자열로 처리.

실제 구현: clap 인수 파싱 단계에서 IpAddr로 직접 파싱하여 잘못된 IP 주소 입력을 CLI 레벨에서 즉시 거부한다.

트레이드오프: 검증이 런타임보다 이르게 발생. hostname 형식은 허용하지 않음. loopback enforcement가 is_loopback() 체크로 단순화됨.

관련 커밋: 944ca53

DEV-03 loopback 범위: 127.0.0.1 단일 → is_loopback() (127.0.0.0/8 + ::1) serve

사양 원문: 127.0.0.1 엄격 바인딩 명시.

실제 구현: IpAddr::is_loopback()을 사용하므로 127.x.x.x 전체 및 IPv6 ::1도 허용.

보안 영향: 127.0.0.0/8 전체는 모두 loopback이므로 실제 LAN/WAN 노출 없음. 일반 HTTP/1.1 브라우저 트래픽 기준으로는 동등.

관련 커밋: 944ca53

DEV-04 tool_call_to_result 엣지: dangling-only → matched self-loop 추가 graph

사양/plan 원문: dangling tool_result에 대해서만 tool_call_to_result 엣지를 emit한다.

실제 구현: matched call (tool_result payload가 tool_call 노드에 병합된 경우)도 self-loop 엣지를 emit하되 attributes.merged = true를 설정한다. (from == to == tool_call node id)

이유: graph 소비자가 결과 존재 여부를 엣지로 쿼리할 수 있어야 하며, 단순 노드 payload lookup보다 그래프 traversal이 일관됨. 결정론 테스트에서 이 동작을 검증.

관련 커밋: 2673333, 5fdc9ff

DEV-05 by_event_uuid 병합 후 result UUID 재매핑 graph

사양 원문: 명시 없음 (구현 세부사항).

실제 구현: graph::compute에서 tool_result payload를 tool_call 노드에 병합한 뒤, by_event_uuid[result_uuid]를 surviving call 노드를 가리키도록 갱신한다.

이유: message_reply 엣지가 result uuid를 참조할 때 dangling edge가 되는 것을 방지. UUID 재매핑 없이는 "sidechain" 시나리오 테스트가 실패함.

관련 커밋: 2673333, 5fdc9ff

DEV-06 host_allowlist 미들웨어: Host 헤더 부재 시 uri.authority() fallback api

사양 원문: Host 헤더 기반 allowlist 검사 명시.

실제 구현: Host 헤더가 없으면 uri.authority()를 대신 사용해 allowlist를 검사한다. 헤더도 authority도 없으면 통과.

이유: axum-test의 in-process HTTP 테스트 클라이언트가 Host 헤더를 포함하지 않음. 실제 HTTP/1.1 브라우저는 항상 Host를 전송하므로 프로덕션 보안 등가.

관련 커밋: cd6398f

DEV-07 FileHistorySnapshotRecord: sessionId 미파싱 ingest

사양 원문: 모든 JSONL record 타입에서 session_id 추출 기대.

실제 구현: 실제 JSONL file-history-snapshot 레코드에 sessionId 필드가 없음. 파싱 시 빈 session_id로 저장되며 세션 범위 쿼리에서 제외됨.

영향: file-history-snapshot ObservedEvent는 DB에 저장되지만 /v1/sessions/{id} 응답에 포함되지 않음.

후속 작업: 인접 레코드의 session_id를 역방향으로 전파하는 로직이 필요 (future slice).

관련 커밋: 38b6439, b077ca5

02Known Gaps / Follow-ups

아래 항목은 사양에서 정의되었으나 slice-1 범위에서 구현되지 않은 기능 및 추후 슬라이스에서 해결해야 할 사항이다.
  • No live tail / file watcher. ingest를 재실행해야 새 JSONL 라인을 수집한다. 멱등(idempotent).
  • No redaction. --all 인제스트는 raw JSONL에서 secrets를 그대로 수집할 수 있다. 사용 전 주의 필요.
  • Pagination hard limit only. next_cursor는 항상 null. 커서 기반 페이지네이션 미구현.
  • No MCP server. MCP Streamable HTTP endpoint는 later slice.
  • No UI. causal replay, why panel, finding 등 UX는 later slice.
  • No findings engine. Finding / RootCauseHypothesis / QualitySummary 생성 미구현.
  • SystemRecord fixture 없음. 실제 JSONL에 type=system 레코드 2건이 존재하나 테스트 fixture 미포함.
  • _sqlx_migrations bin version 검증 미구현. serve 명령은 observed_event 테이블 존재 여부만 확인하고 migration 버전을 검증하지 않는다.
  • OTel / Hook / File-Git 수집기 없음. transcript JSONL만 지원. 나머지 source layer는 later slice.

05Slice-2 Intentional Deviations

DEV-S2-01 event_id lookup key instead of event_uuid api

사양 원문: event_uuid를 raw record lookup key로 명시.

실제 구현: observed_event PK인 event_id (ULID)를 사용. 일부 레코드 타입(file-history-snapshot)은 event_uuid를 포함하지 않아 event_uuid만으로는 모든 이벤트를 식별할 수 없음. 클라이언트는 graph_node.source_event_ids[0]를 사용해 event_id를 참조한다.

영향: API path는 /v1/events/:event_id/raw. 기존 event_uuid 기반 참조가 있다면 event_id로 전환 필요.

DEV-S2-02 SPA fallback returns 200 for unknown routes serve

사양 원문: 명시 없음 (SPA routing 세부사항).

실제 구현: axum .fallback(spa_handler)는 non-asset path에 대해 index.html을 status 200으로 반환한다. SPA의 * 라우트가 클라이언트 측에서 "not found"를 표시한다.

이유: deep-link refresh가 정상 동작해야 하므로 의도적. /random-path로 접근해도 200이 반환되며 SPA가 라우팅을 처리한다.

DEV-S2-03 webui/dist/ is build-required, not committed toolchain

사양 원문: 명시 없음 (빌드 아티팩트 관리 세부사항).

실제 구현: webui/dist/는 완전히 gitignore 처리됨. README 및 justfile에서 just webui-build를 cargo build 전에 실행하도록 안내. build.rs 자동화를 통한 통합은 cargo-only 소비자에게 Node 툴체인을 강제하게 되므로 채택하지 않음.

트레이드오프: 빌드 단계가 명시적이고 분리됨. rust-embed가 dist 파일을 컴파일 시점에 포함하므로 webui-build 없이 cargo build하면 embedded SPA가 없는 바이너리가 생성됨 (static_serve 테스트 실패 포함).

DEV-S2-04 Lane mapping is client-side webui

사양 원문: 명시 없음 (lane 분류 책임 소재).

실제 구현: node_kind → lane 매핑은 TypeScript 상수 (webui/src/api/laneMapping.ts)에 정의됨. 서버 응답에는 포함되지 않음.

트레이드오프: 새로운 node_kind가 추가되면 webui 변경이 필요하지만, 서버 응답 스키마는 안정적으로 유지됨. 서버 사이드 lane 매핑은 API 계약 변경 없이 클라이언트 독립적 진화를 방해함.

DEV-S2-05 source.kind passes raw DB value api

사양 원문: source.kind를 정규화된 값(예: "transcript")으로 반환.

실제 구현: endpoint는 raw raw_event.source_type 값 ("claude_transcript")을 그대로 반환함. ingest layer의 식별자와 직접 추적 가능하며 정규화 레이어 없이 provenance를 보존함.

영향: 클라이언트가 "transcript"가 아닌 "claude_transcript"를 기대해야 함. 추후 정규화 레이어 추가 시 breaking change 가능.

08Slice-3 Intentional Deviations

DEV-S3-01 OTLP/JSON only (no protobuf) api

OTLP/HTTP은 protobuf와 JSON 둘 다 지원하지만 slice-3는 JSON만 받는다. SDK 측에서 OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/json 설정 필요.

DEV-S3-02 Traces only — no metrics/logs api

metrics는 time-series 모델이라 ObservedEvent에 직접 매핑되지 않고, logs는 traces가 가진 인과 정보 없이 양만 늘린다. 두 signal은 후속 슬라이스.

DEV-S3-03 Telemetry facet stored inside payload JSON model

DB schema 변경 회피를 위해 facet은 payload.telemetry 키 아래 포함된다. trace_id/span_id/parent_span_id/ latency_ms는 top-level 컬럼 사용 — 인덱스 가능.

DEV-S3-04 No transcript ↔ OTel merge in slice-3 graph

Transcript producer가 아직 trace_id를 emit하지 않으므로 merge가 자동 발생하지 않는다. graph_node의 merge_keys에 trace_id+span_id는 깔려 있어 producer 추가 시 자동 동작.

DEV-S3-05 No span_parent edges; otel_span nodes excluded from turn_order graph

parent_span_id는 column에 저장되지만 span_parent edge kind는 아직 emit하지 않는다. turn_order edge는 conversation turn 의미라 otel_span 노드는 명시적으로 필터한다. 데이터 경로 우선 검증 후 후속 슬라이스에서 cross-kind correlation을 추가.

DEV-S3-06 list_sessions filters out empty session_id api

OTel span이 session.id attribute 없이 들어오면 DB에 빈 문자열로 저장된다. GET /v1/sessions는 WHERE session_id != ''로 이런 행을 응답에서 제외 — spec §6.3 에 정의된 동작.

DEV-S3-07 otel::store: rebuild graph on every POST, including duplicate-raw POSTs graph

사양 원문: 명시 없음 (graph staging policy 세부사항).

최초 구현 (post-merge에서 발견된 갭): otel::store는 observed_event 행만 삽입하고 rebuild_session을 호출하지 않았다. 결과적으로 HTTP 경로(POST /otel/v1/traces)에서 ingest 직후 GET /v1/sessions/:id/graph가 404를 반환했다. 테스트는 build::rebuild_session을 명시 호출해서 통과했기에 회귀 검출이 안 됐다. fix는 store 내부에서 touched 세션마다 자동 rebuild를 호출 (커밋 21527b9).

두 번째 갭 (self-heal): raw dedup이 발동하면 continue로 루프를 빠져 나가 touched에 session_id가 들어가지 않는다 → rebuild도 skip. 결과적으로 이전 버그 바이너리가 만든 stale state(observed_event row 있음, graph_node 없음)는 새 바이너리에서 같은 fixture를 재POST해도 자가복구되지 않는다. fix는 touched.insert를 dedup 체크보다 먼저 실행 (커밋 78b2f30).

채택한 정책: "ingest event는 항상 affected session의 graph rebuild를 유발한다. raw row 중복 여부와 무관." graph_node는 observed_event로부터 결정론적으로 파생되는 view이므로 DELETE + 재INSERT는 idempotent. 데이터(raw_event, observed_event)는 절대 교체되지 않는다 — graph view만 source-of-truth 기준으로 다시 빌드된다.

트레이드오프:

  • 장점: self-heal (바이너리 업그레이드/crash 후 재POST로 복구), end-state idempotency, 단일 세션 rebuild 비용은 SQLite 로컬에서 sub-ms.
  • 단점: 고volume retry 환경(예: OTel SDK가 같은 batch를 초당 수십 번 쏘는 시나리오)에서 데이터 변화 없는 rebuild가 누적될 수 있음. slice-3 단일 사용자 scale에선 무시 가능.

재검토 트리거: 다음 중 하나라도 발생하면 정책 변경 후보:

  • 고volume OTel ingestion (retry 폭주 패턴 관측)
  • multi-source ingest 추가(Hook/File-Git)로 session-level rebuild 비용 증가
  • graph_node에 idempotent하지 않은 side-effect 추가(예: ext index, notification)

대안 옵션 (현재 미채택):

  • Option D — recovery-only rebuild: if !inserted && graph_node_count(session) == 0 { rebuild }. duplicate인데 graph가 이미 있으면 skip. 단점: stale graph가 일부만 비어 있는 경우 감지 불가.
  • Option E — dirty flag: 세션별 graph_dirty 비트. 새 observed_event 삽입 시 set, rebuild 후 clear. 시작 시 dirty 세션 스캔. 가장 정교하지만 추가 schema + lifecycle 필요.

관련 커밋: 21527b9 (initial fix), 78b2f30 (self-heal extension).

11Slice-4 Intentional Deviations

DEV-S4-01 External hook vs transcript-internal hook merge_keys split via parser_version graph

사양 원문: 명시 없음 (graph merge_keys 세부사항).

실제 구현: graph::build::compute의 EventKind::HookEvent branch가 e.parser_version.starts_with("hook@")로 분기한다. 외부 hook (slice-4)은 (session_id, hook_event_name, tool_use_id)로 merge하고, transcript-내부 hook attachment (slice-1)는 기존 event_uuid merge_keys를 유지한다.

이유: 두 source의 식별 키가 본질적으로 다르다. 외부 hook은 hook_event_name + tool_use_id로 의미적 동일성을 가지지만 event_uuid는 없다. 반대로 transcript-내부 hook은 부모 message의 event_uuid로만 식별 가능. 둘을 같은 merge_keys 스키마로 강제하면 한 쪽이 항상 dangling이 된다.

후속: tool_use_id 기반 cross-source dedup은 별도 slice. 현재는 외부/내부가 별도 노드로 공존한다.

DEV-S4-02 Pass-through body shape (no wrapper envelope) api

사양 원문: 명시 없음.

실제 구현: Claude Code의 stdin JSON을 그대로 받는다. wrapping object ({"events": [...]}) 없이 단일 hook object 또는 JSON array 직접. 전체 JSON 본문이 그대로 raw_event.payload에 저장됨.

이유: 사용자 forward script가 cat | curl --data-binary @-로 단순해진다. wrapping을 추가하면 user-side script가 jq 등으로 변환해야 하며, 그 변환은 hook 페이로드 보존성을 해친다.

DEV-S4-03 1 MB body limit (vs OTel's 4 MB) api

실제 구현: MAX_HOOK_BODY = 1 * 1024 * 1024. OTel receiver는 4 MB.

이유: 단일 hook event는 대부분 수 KB. 1 MB는 batch 50~100건 수준이며 hook의 high-frequency 특성과 fail-soft 요구를 고려하면 적절. OTel은 batch span 수가 더 많아 4 MB가 필요했음.

DEV-S4-04 Forward script not auto-installed ops

사양 원문: CLAUDE.md 명시적 non-goal — "Claude Code 설정 / hook / command / skill / memory 변경".

실제 구현: README에 forward script 예제와 settings.json 스니펫만 제공. witmcc init-hooks 같은 자동 설치 서브커맨드는 없음.

이유: Claude Code 설정에 대한 write는 product principle 위반. 사용자가 명시적으로 hook을 등록해야 데이터가 들어온다.

DEV-S4-05 Hook ↔ transcript-internal hook 중복 미해결 (known gap) model

현황: Claude Code가 PreToolUse hook을 트리거하면 외부 hook (이 slice의 forward script로 들어옴)과 transcript-내부 hook attachment 두 경로로 동일 사건이 기록될 수 있다. graph_node는 각각 별도 노드로 보존된다.

이유: transcript-내부 hook attachment는 hook_event_name을 명시적으로 carry하지 않으며, 외부 hook은 event_uuid를 갖지 않는다. cross-source dedup은 시간 윈도우 + tool_use_id 휴리스틱이 필요하며 별도 slice.

영향: tool 사용 횟수가 두 source 모두 활성일 때 부풀려 보일 수 있음. by_kind.hook_event count 해석 시 주의.

DEV-S4-06 No DDL migration (raw_event/observed_event schema 그대로 재사용) db

사양 원문: 명시 없음.

실제 구현: migration 추가 없음. source_type이 TEXT column이라 "hook" 값 추가에 schema 변경 불필요. 기존 OTel slice의 0002_telemetry.sql 인덱스도 그대로 적용된다.

14Slice-5 Intentional Deviations

DEV-S5-01 Synthetic session_id = "filesystem" model

사양 원문: spec §4 (CLI Surface) — file/git 이벤트는 Claude Code session에 자동 귀속되지 않으며, 합성 well-known id "filesystem"로 emit한다고 명시.

실제 구현: FILESYSTEM_SESSION_ID 상수. 모든 store_file_event / store_commit가 이 id를 사용. GET /v1/sessions에 일반 세션처럼 표시되며, /v1/sessions/filesystem/graph로 file_event / git_commit / diff_hunk 노드를 보여준다.

후속: 시간 윈도우 + cwd overlap 휴리스틱으로 실제 Claude session에 re-key 하는 작업은 별도 slice.

DEV-S5-02 Git poller startup: HEAD 이전 commit replay 생략 collector

사양 원문: spec §9.3 — "on startup, replay any commits since the last git_commit row in DB".

실제 구현: run_git_poller 시작 시 last_seen = HEAD OID로 초기화. DB의 마지막 git_commit row를 조회하지 않는다. 이후 tick부터 새 commit만 ingest.

이유: 큰 repo에서 처음 시작 시 수십만 commit replay는 startup 비용이 과도하다. dedup으로 무결성은 보장되나 시간이 길어진다. slice-5 범위에서는 startup 이후 새 commit observability가 핵심 가치이며, 과거 commit ingest는 별도 backfill 서브커맨드로 분리 가능.

영향: serve 재시작 사이의 commit은 놓칠 수 있음. watcher와 poller가 항상 떠 있는 사용 패턴이면 무관.

DEV-S5-03 git2 객체는 spawn_blocking으로 격리 runtime

현황: git2::Repository와 그 파생 객체 (Commit, Revwalk, Patch)는 raw FFI pointer를 보유하며 !Send다. tokio::spawn future 안에서 직접 사용하면 컴파일 에러.

실제 구현: git_poller::extract_new가 모든 git2 작업을 동기 함수로 캡슐화한 뒤 tokio::task::spawn_blocking로 실행. 추출된 Vec<(CommitRecord, Vec<HunkRecord>)>는 plain data여서 await 가능.

DEV-S5-04 Deterministic diff_hunk_id = "hunk_{sha}_{idx}" id

사양 원문: §5.7 hunk payload에 ULID 권고.

실제 구현: commit SHA + 추출 순서 index로 deterministic id 생성. 동일 commit을 두 번 ingest하면 같은 id이므로 diff_hunk 테이블의 PRIMARY KEY로 dedup되고 canonical-JSON sha256으로 raw_event dedup된다.

이유: ULID 사용 시 동일 commit re-ingest가 새 행을 만든다 (raw dedup은 막지만 diff_hunk 테이블은 별도 ID). Deterministic id면 두 단계 모두 idempotent.

DEV-S5-05 250 ms in-memory debounce (no notify-debouncer-full) collector

사양 원문: §8 — "250 ms debounce coalesces them".

실제 구현: HashMap<(PathBuf, FileChange), Instant> + 100 ms ticker. Editor의 unlink+create+chmod 시퀀스가 단일 file_event 한 건으로 flush됨.

후속: 부하 환경에서 이벤트 누락이 관측되면 notify-debouncer-full로 교체. 슬라이스 5 범위에서는 수동 dependency 최소화.

DEV-S5-06 vendored-libgit2 기본 활성화 build

DEV-S5-07 Patch preview 4 KB 절단, hunk 2000건 cap storage

사양 원문: §5.7 — "truncated to 4 KB", §8 — "MAX_HUNKS_PER_COMMIT = 2000".

20Slice-7 Intentional Deviations

DEV-S7-01 Cursor strategy: rehash whole file instead of byte-offset map

사양 원문: design spec §6.1 proposed an in-memory HashMap<PathBuf, u64 byte_offset> seeded from raw_event on startup.

구현: transcript_tail::run re-calls ingest::store::ingest_file(pool, path) on every debounced flush. The existing UNIQUE(source_uri, source_line_no, payload_sha256) constraint absorbs duplicates so no cursor state is needed.

트레이드오프: every flush rehashes the whole file (slice-1 stream_file reads the entire JSONL again, computes per-line sha256). Bounded by Claude Code's per-session JSONL size (typically MB-scale; bahamoth's largest at smoke time was a few MB). In exchange: zero cursor state to corrupt, no migration, and the live tail shares its entire codepath with ingest --all so any slice-1 bugfix benefits both.

후속: byte-offset cursor is a future optimisation if/when users report large transcripts hot-spotting the watcher.

DEV-S7-02 Initial catch-up scan runs in a background task

증상: first impl awaited the catch-up scan inline, which made witmcc serve startup time = total transcript bytes / parse rate. CI test serve_accepts_watch_and_poll_flags (8s budget) failed because the test host's real ~/.claude/projects contained too many MB to scan in time.

구현: scan_initial is spawned into a dedicated tokio task wrapped in tokio::select! on cancel.cancelled(). Serve startup is now instantaneous; the notify watcher picks up live writes regardless of whether catch-up is still running. UNIQUE constraint absorbs any race.

DEV-S7-03 Transcript tail is on by default

맥락: the whole slice exists because the user wanted "한번에" — making the tail opt-in would have defeated the goal.

구현: default-on; opt-out via --no-watch-transcripts. Two existing tests (tests/cli_serve.rs::serve_accepts_watch_and_poll_flags and tests/doctor.rs::spawn_server) pass the opt-out so they do not depend on the test host's real transcripts root state.

DEV-S7-04 Recommendations now consult effective_env, not process env

증상: v0.1 build_recommendations only looked at report.envs (process env), so users who had OTel keys in ~/.claude/settings.json's env block (which is the documented way to configure Claude Code) got a misleading "Set the following…" recommendation.

DEV-S7-05 Project walk stops at .git even without .claude/

DEV-S8-12 session_graph race + SessionDetailPage 깜빡임

증상: 사용자가 라이브 stream 보는 중 Timeline marker가 주기적으로 사라지고 “no observations in this session” 메시지로 깜빡거림. 잠시 후 다시 marker 등장 → 반복.

원인: graph::build::rebuild_session이 DELETE + INSERT를 transaction 없이 수행. ingest_file이 새 transcript line마다 호출 → DELETE와 INSERT 사이 ms 동안 graph_node 0 rows. SessionDetailPage가 그 시점에 refetch하면 session_graph handler의 if nodes.is_empty() → 404 trigger. 클라이언트는 404를 잡아 빈 graph로 처리 → Timeline 깜빡임.

fix (2-layer):

  1. server: session_graph가 빈 nodes에도 200 반환. 빈 graph는 valid transient state.
  2. client: refetch가 빈 graph 받으면 이전 graph state 유지 (race가 self-resolve할 시간 확보).

잔여: rebuild_session 자체를 sqlx::transaction으로 wrap. 별도 commit으로 진행 예정. commits c6102c8, 8a25ac7.

DEV-S8-13 SessionDetailPage refetch 폭주로 renderer freeze

증상: 사용자 페이지가 1~2분 안에 frozen (CDP timeout 45s). eventCount 갱신 멈춤.

원인: envelope 매 도착마다 refetch → GET 4000+ events JSON (~200KB) + Timeline 3500+ SVG circle 재생성. active 세션에서 envelope/sec이 setState burst를 유발. main thread block.

  1. refetch trailing-debounce 250ms → 1000ms.
  2. setState identity-skip: 새 graph가 이전과 node/edge/event_count + latest event_id 모두 동일하면 prev state reference 그대로 반환 → React가 Timeline re-render 자체 skip.

잔여: spec §6.2 envelope inline append 본격 구현이 진짜 fix. slice-9 windowed buffering 작업에 포함. commits 8a25ac7, 4abf612.

DEV-S8-14 GET /v1/sessions/:id가 oldest 5000만 반환 → newest 안 보임

26Slice-9 Intentional Deviations

DEV-S9-01 spec §4.3 — next_cursor "live tip" 판정

맥락: spec은 "the window's last row equals session_summary.last_observed_at" 일 때 next_cursor: null이라고 했다. RFC3339 표현에서 동일 시각의 둘 이상의 row가 존재할 수 있다 (DEV-S8-10 cross-source ordering).

구현: last_observed_at 문자열 비교만 한다. 같은 second 안에 여러 row가 있어도 last row가 last_observed_at과 일치하면 live tip으로 본다. client는 next_cursor가 null일 때 SSE 구독으로 갈음하므로 fetch 추가 round-trip이 없을 뿐 실제 손실은 없다.

DEV-S9-02 spec §5.2 — envelope이 ObservedEvent로 변환

맥락: spec은 envelope 도착 시 getSessionEvents(after=newest, limit=50) 로 incremental fetch 권고. 하지만 SSE envelope이 이미 event_id, observed_at, kind, session_id, source_type을 carry한다 — useSessionWindow의 append에 충분.

구현: envelopeToObserved()가 envelope을 부분 ObservedEventDto로 변환하여 직접 appendOne. raw_event_id / actor / payload 등은 default("", "unknown", {}) — 어차피 Timeline은 graph 기반 렌더이므로 이 값들이 사용되지 않는다.

리스크: 향후 Timeline이 events 기반 렌더로 옮기면 변환 손실이 visible. 그때는 envelope → /v1/events/:id/raw fetch 또는 server-side enriched envelope으로 변경.

DEV-S9-03 spec §5.1 — LRU trim 절대값 → 비율

맥락: spec은 maxEvents=5000일 때 trim=500 (10%)로 명시.

구현: LRU_TRIM_RATIO = 0.1로 동적 계산 (Math.max(1, Math.floor(maxEvents * 0.1))). vitest에서 maxEvents=5 같은 작은 값을 써도 trim이 합리적으로 동작 (1 row drop). 5000 prod path는 spec과 동일하게 500 trim.

DEV-S9-04 spec §5.4 — IntersectionObserver fake for vitest

맥락: jsdom은 IntersectionObserver를 제공하지 않는다. SessionDetailPage가 mount 시 IO를 생성하면 첫 effect에서 throw.

구현: webui/src/test/setup.ts에 no-op IntersectionObserver 전역 shim을 항상 install. 실제 트리거가 필요한 테스트(IO triggers loadOlder)는 vi.stubGlobal로 per-test override. EventSource shim과 동일한 패턴.

DEV-S9-05 L3 subprocess: 10000 → 1200 events

맥락: spec §6 L3는 10000-event 시드를 명시. 실 DB I/O 부담을 줄이려고 1200 events × 200-per-page = 6 pages로 진행.

구현: tests/events_subprocess.rs가 1200 events file-backed WAL DB 시드 + 6 페이지 backwards paging + union 정합성 검증 + live-tip ?after= 빈 응답 검증. L3 의도(real HTTP, real subprocess, full reconstruction)는 그대로 만족. 10000-event 부하 검증은 browser smoke에서 53k events 실 DB로 직접 확인되었으므로 별도 fixture 불필요.

DEV-S9-06 spec §6.2 — Timeline 자체 변경 없음

맥락: 사용자 제안(슬라이스 8 round 2)의 video-streaming 패턴은 viewport virtualization + SVG dynamic culling을 함의했다.

구현: slice-9 scope는 server range query + client window/cache까지. Timeline SVG 자체의 virtualization은 slice-10. 사용자의 53k event DB에서도 Timeline은 graph 기반 렌더이므로 (graph node 수는 events 수의 일부) 현재 deepest 케이스에서도 brownser freeze 없음 (browser smoke 확인). 진짜 viewport-only 렌더링은 graph 자체가 5k+ 노드를 가질 때 필요.

DEV-S9-07 graph refetch — debounce + interval 분리

맥락: envelope 도착 시 graph는 어차피 stale. spec은 "50 envelopes 또는 10s interval"로 graph refresh를 trigger하라 했다.

구현: 두 메커니즘 분리. (a) envelope arrival → 800ms trailing debounce로 getGraph만 호출. (b) 별도 10s setInterval로 getSession (summary) refresh. envelope count 임계값 기반은 사용하지 않음 — debounce가 이미 burst를 흡수하고, summary는 idle-friendly cadence가 더 정확.

37slice-15 — Insight Engine L2 infra (judge infrastructure) (2026-05-27)

Overview (slice-15)

목표
LLM judge 인프라 (JudgeProvider trait + 세 가지 구현 + cache + budget guard + runtime)를 배선하고, L2 경로를 테스트하되 production finding category는 추가하지 않는다.
JudgeProvider trait
async fn judge(&self, prompt: JudgePrompt) -> Result<JudgeVerdict, JudgeError>. model_id() + prompt_template_version()는 cache key 재료. async_trait crate 사용 (object-safe async trait).
세 가지 구현
  • NoopJudge: 항상 Err(Disabled) 반환. 기본값. LLM 호출 없음.
  • FixtureJudge: JSON 파일에서 "category||evidence_hash" 키로 verdict 조회. judge_with_hash() helper — 테스트에서 미리 알려진 hash로 직접 조회.
  • AnthropicJudge: hand-rolled reqwest (DEV-S15-05). prompt caching via cache_control: ephemeral. prompt_template_version() = SHA-256 of src/insight/judge/prompts/judge_v1.txt.
CachedProvider<P>
SQLite 캐시. Cache key = sha256(category||"\0"||model_id||"\0"||template_version||"\0"||evidence_hash) where evidence_hash = sha256(canonical_json(evidence_projection)) (key-sorted JSON). Cache hit → DB에서 serve, inner 호출 없음, budget 소비 없음 (DEV-S15-04/07).
BudgetGuard<P>
per-rebuild AtomicUsize counter. 0이 되면 Err(BudgetExhausted). Cache가 Budget 안쪽 — hit는 budget 소비 안 함.
JudgeRuntime
factory pattern: Arc<dyn Fn(metrics, budget) -> Box<dyn JudgeProvider>>. build_for_rebuild()이 매 rebuild마다 fresh BudgetGuardDyn을 생성 (DEV-S15-02). concurrent rebuild = 각자 독립 budget.
findings_pending_judge
budget exhausted / disabled / transport error 시 candidate를 queue에 보존. 다음 rebuild 시 drain. monotone progress 보장 (절대 silently drop 없음). INSERT OR IGNORE로 idempotent — 이미 pending인 candidate 덮어쓰지 않음.
PromotionPolicy routing
  • Always → L1 direct promote (judge 없음). tool_failure, missing_verification이 여기.
  • Never → 항상 judge 통과. Disabled/Budget → pending queue.
  • IfAbove(t) → confidence > t면 L1 promote; 이하면 judge 경로.
test-helpers feature
NoopTestExtractor는 cfg(test)가 아니라 feature = "test-helpers"로 guard. 이유: integration test binary는 lib을 test 모드로 컴파일하지 않아 cfg(test)가 lib code에서 inactive됨. [[test]] required-features = ["test-helpers"]로 해당 통합테스트만 opt-in.
/v1/health insight block
judge_kind, judge_calls_24h, judge_pending_count, judge_cache_hits_24h, judge_cache_misses_24h, judge_budget_exhaustions_24h. AtomicI64 counters — in-memory, server restart 시 reset (DEV-S15-03).
CLI
witmcc serve --judge {none|anthropic|fixture} --judge-budget N --judge-fixture-path <path>. none은 noop의 alias. Default = none (L2 OFF).

38slice-16 — Insight Engine L2 Categories (2026-05-27)

Overview (slice-16)

Closes M5 (Insight engine) and AC-4. Ships three finding categories that require the L2 LLM judge: risky_action, context_bloat, final_state_mismatch. All three use PromotionPolicy::IfAbove(1.0) — they never promote without a judge verdict. With --judge none (default) they are dormant (queued to findings_pending_judge).

risky_action

Fires on: (a) Bash tool_call whose input.command matches the destructive-pattern allowlist (rm -rf, git push --force, git reset --hard, sudo rm, etc.), OR (b) any diff_hunk.user_modified == true. L1 confidence 0.7. Judge decides: was the action user-directed and intentional, or unsupervised drift?

context_bloat

Fires when: tool_result content > 50 KB AND next assistant_message found within 3 events AND no downstream tool_call contains ≥ 3 stem overlaps with the bloat content. L1 confidence 0.5. Judge decides: reused vs. wasted.

final_state_mismatch

Fires when: first user_message contains a goal verb from the frozen lexicon (fix, add, implement, etc.) AND last verification_run status is failed AND final assistant_message has no completion marker (done, fixed, etc.). Session-level grain (DEV-S16-06): at most 1 finding per session. L1 confidence 0.6.

Redaction shim (DEV-S16-05)

src/insight/redaction_shim.rs ships as a no-op placeholder. All projection _redacted fields call redaction_shim::apply_text() which passes text through unchanged and emits a tracing::warn! per call (so the lapse is visible in dev logs). Slice-18 replaces this with the real redaction gate. Test tests/redaction_shim_lock.rs asserts the shim is a no-op — will be converted (not deleted) in slice-18.

34Overview (slice-19) — Token Auth + Retention Sweep (MVP Exit)

브랜치: feat/remaining-milestones · 날짜: 2026-05-27 · AC: AC-6 closed. M7 (Hardening) closed. MVP 완료.

slice-19는 Access Control + Data Lifecycle 두 기능을 추가하여 MVP를 종료한다.

Token Authentication

  • Token generation: 32바이트 CSPRNG → base64url → witmcc_<43-char> 형식 (~50자)
  • Token file: $WITMCC_CONFIG_DIR/token (미설정 시 ~/.config/witmcc/token), mode 0600 POSIX. 과잉 권한이면 기동 거부.
  • Middleware: require_token — Authorization: Bearer <token> 헤더 검증. subtle::ConstantTimeEq 사용 (타이밍 사이드채널 방어).
  • Coverage: 모든 /v1/* + /mcp 라우트 auth-gated. /otel/*, /hooks/*, /v1/stream, static SPA는 열린 상태.
  • CLI flags (serve 서브명령): --print-token (token 출력 후 exit 0), --rotate-token (atomic 교체 후 exit 0).

Retention Sweep

  • Profiles: none (기본, 삭제 없음) | default (raw 30d, normalized 180d, audit 90d, judge_cache 30d) | strict (raw 7d, others 30d)
  • Sweep task: tokio::spawn, 6시간 주기. none 프로파일에서는 기동 안 함.
  • Tombstones: 삭제된 resource_id는 retention_tombstone 테이블에 기록. Pull API에서 해당 ID 요청 시 410 Gone 반환 (404와 구분).
  • Audit row: 각 sweep 실행 후 audit 테이블에 retention.deleted 이벤트 기록.

New Endpoints

  • GET /v1/audit — 최근 audit 행 200개. Auth-gated.
  • GET /v1/health — security 블록 추가: auth_required, retention_profile. Auth-gated (DEV-S19-02).

New Migrations

  • 0012_retention.sql — retention_tombstone 테이블
  • 0013_audit.sql — audit 테이블 + idx_audit_created

Doctor Integration

witmcc doctor가 WITMCC_CONFIG_DIR/token을 자동으로 읽어 Bearer 헤더를 추가. 401 응답을 "server reachable" (not connectivity error)로 처리.

Smoke Evidence

  • witmcc serve --print-token → stderr에 witmcc_… 출력, exit 0. Token file mode 0600 확인.
  • curl /v1/health → 401 (no token)
  • curl -H "Authorization: Bearer $T" /v1/health → 200, security.auth_required: true, security.retention_profile: "none"
  • curl -H "Authorization: Bearer wrong" /v1/health → 401
  • POST /mcp without token → 401; with token → 200
  • witmcc serve --rotate-token → 새 token 파일 기록, stderr 출력, exit 0
  • 단위 테스트: sweep_default_profile_deletes_raw_older_than_30d, deleted_resource_has_tombstone, sweep_writes_audit_row → 모두 green

Intentional Deviations (slice-19)

DEV-S19-01Retention default is none, not default.
보안 사양은 30/180/90일을 기본으로 명시하지만, MVP에서 사용자 raw payload를 기본 삭제하는 것은 놀라운 동작. 기능은 완전히 구현되어 있으며 --retention-profile default 또는 strict로 opt-in.
DEV-S19-02/v1/health is auth-gated (defence-in-depth).
사양은 명시하지 않음. localhost bind가 이미 외부 노출을 막지만, DNS rebinding 공격 방어를 위해 health도 token 필요. 외부 모니터링 도구는 token을 포함해야 함.
DEV-S19-03Token은 per-installation, not per-client.
다중 클라이언트 토큰은 post-MVP. 현재 설치당 하나의 durable token.
DEV-S19-04Tombstones live forever.
~80바이트/tombstone로 크기가 작고, 잃어버리면 410 대신 404가 되는 정도. 수동 정리는 post-MVP.
DEV-S19-05Audit table introduced in slice-19 (not earlier slices).
이전 slice들의 사양에서 audit row를 언급했으나 테이블이 없었음. slice-19에서 테이블과 함께 backfill.
DEV-S19-06--rotate-token은 running server에 즉시 영향 없음.
설계 사양은 "existing connections receive 401 on next request"라고 했으나, token은 serve 시작 시 AppState에 로드된다. rotation 후 새 서버 기동이 필요. 사양의 "hot reload" 의미는 post-MVP 개선사항.
DEV-S19-07subtle::ConstantTimeEq for token comparison.
로컬 전용 토큰에서는 기술적으로 overkill이지만 런타임 비용이 없고 미래 보안 리뷰에서 지적받을 여지를 없앰.
DEV-S19-08--auth flag, default off (post-slice-19 follow-up).
단일 사용자 dev 환경에서 브라우저 WebUI 접근 시 401이 빈번하여 사용성이 깨졌다. --auth on|off 플래그를 신설, default off로 두어 token 기반 미들웨어가 자동 bypass되도록 함. token capability는 코드에 그대로 남아 --auth on으로 opt-in 가능 — AC-6은 capability 기준으로 여전히 green. retention default(none, DEV-S19-01)와 동일 정책. 미들웨어는 state.token.is_empty()에서 이미 분기를 갖고 있어 추가 변경 없음 — CLI/main에서 token을 만들지 말지만 선택.

telemetry fold (Group A) — Slice 1/3 (2026-05-31)

브랜치: facet-fold-episode-redesign · 날짜: 2026-05-31 · 트랙: telemetry-fold / episode-redesign epic(슬라이스 1/3). Spec: docs/superpowers/specs/2026-05-31-telemetry-facet-fold-and-episode-redesign-design.md, Plan: docs/superpowers/plans/2026-05-31-telemetry-fold-slice1-group-a.md.

직전 facet correlation 슬라이스는 deterministic하게 연관되는 telemetry를 독립 노드 + facet_of 엣지로 표현했다. 이 슬라이스는 그 방식을 대체한다 — telemetry를 별도 노드로 materialize하지 않고 소유 노드의 payload.facets 배열로 fold한다.

무엇이 바뀌었나

그래프 빌더(src/graph/build.rs::compute())가 deterministic하게 연관되는 telemetry를 소유 그래프 노드의 payload.facets 배열로 fold한다. 각 telemetry를 독립 노드로 materialize한 뒤 facet_of 엣지로 잇던 방식은 폐기됐다 — facet_of 엣지는 더 이상 emit되지 않는다.

fold되는 4종 + 상관 키 (deterministic)

  • llm_request OTel span → assistant_message, 키 request_id (raw_span.attributes[]에서 flatten_attrs로 추출). span duration + token 행 + trace 정보를 운반.
  • api_request log_record → assistant_message, 키 request_id (payload.attributes.request_id). cost_usd·duration_ms·model·토큰을 운반.
  • tool_result log_record → tool_call, 키 tool_use_id (payload.attributes.tool_use_id).
  • tool_decision log_record → tool_call, 키 tool_use_id. permission decision(accept/source)을 운반.

facet entry 형태

{
  "facet_kind": "tool_result_log|tool_decision_log|llm_request_span|api_request_log",
  "basis": "tool_use_id|request_id",
  "source_event_id": "<folded event_id>",
  "data": <folded event payload, verbatim>
}

data는 fold된 이벤트의 payload를 그대로 보존한다(Source-preserving 원칙). fold는 기존 상관 맵(assistant_nid_by_request_id, tool_call_nid_by_tid)과 owner-survival 가드(valid_nodes)를 재사용하므로 새 상관 비용이 없다 — 빌더의 단일 O(N) 패스를 그대로 쓴다.

프론트엔드

  • buildEntityFacets가 node.payload.facets를 읽는다(facet_of 엣지 아님).
  • buildToolMetrics가 fold된 tool_*_log facet의 data.attributes를 읽는다.
  • assistant LLM 지표는 fold된 llm_request_span facet에서 parseLlmRequestSpan으로 재구성된다.
  • Raw 탭은 엔티티 + 그 fold된 facet들을 source별 분할 블록으로 렌더한다.

범위 / 이 슬라이스가 하지 않는 것

이것은 3개 슬라이스 중 1번이다. Group-A 4종만 fold한다. 고아(orphan) telemetry는 의도적으로 독립 노드로 남긴다:

  • metric_sample — deterministic owner 없음(Slice 2 → 세션 레벨 facet).
  • hook_event, llm_request가 아닌 span, tool/api가 아닌 log_record (Slice 2 → drop 또는 세션 facet).
  • episode 재설계(Tier1 keep / Tier2 delete, missing_verification raw-derivation)는 Slice 3.
  • raw_event(SSOT)는 절대 수정하지 않는다.

운영 주의 — 스키마 마이그레이션 없음, 재빌드 필요

스키마 마이그레이션 없음 — graph_node.payload는 이미 JSON 컬럼이고, fold는 그 안에 nest되는 내용만 바꾼다. 기존 dev-DB의 graph 행은 fold 이전 형태를 그대로 들고 있다. fold된 행으로 재생성하려면 세션을 다시 빌드해야 한다 — transcript를 재ingest하거나 serve가 빌드하게 두면 된다(serve는 각 OTLP 배치마다, 그리고 시작 시 transcript ingest에서 그래프를 rebuild한다). witmcc init-db는 스키마만 보장하고 데이터를 지우지 않는다 — 완전히 깨끗한 DB가 필요하면 먼저 .witmcc.sqlite*를 삭제한 뒤 init-db를 실행한다.

telemetry fold Slice 2 — orphan telemetry dropped from graph (2026-05-31)

브랜치: telemetry-fold-slice2-groupbc · 날짜: 2026-05-31 · 트랙: telemetry-fold / episode-redesign epic(슬라이스 2/3). Spec: docs/superpowers/specs/2026-05-31-telemetry-facet-fold-and-episode-redesign-design.md.

Slice 1은 deterministic하게 연관되는 telemetry 4종을 소유 노드의 payload.facets로 fold하고, fold된 노드를 그래프에서 제거했다. 그러나 fold 후에도 소유자도 backbone 역할도 없는 "고아(orphan) telemetry" 노드가 그래프에 그대로 남아 있었다. Slice 2는 그 나머지를 그래프에서 제거하여 그래프가 대화/행동 backbone만 담도록 한다.

drop되는 node_kind 4종

  • metric_sample — 데이터 포인트(비용/토큰/지연 등).
  • hook_event — 외부/transcript-internal hook 모두.
  • otel_span — llm_request가 아닌 span(예: claude_code.tool.execution). llm_request span은 Slice 1에서 이미 assistant로 fold되어 사라졌다.
  • log_record — tool_result/tool_decision/api_request가 아닌 log (예: hook_execution_complete, mcp_server_connection). foldable log는 Slice 1에서 이미 owner로 fold되었다.

제거 후 남는 backbone: user_message, assistant_message, tool_call, verification_run, diff_hunk.

핵심: fold-before-drop 순서

orphan-drop은 반드시 Slice 1 fold 패스 이후에 실행되어야 한다. fold는 telemetry 노드의 payload(예: llm_request span의 raw_span)를 읽어 owner로 fold한 뒤 fold된 노드를 제거한다. drop을 fold보다 먼저 하면 foldable telemetry가 fold되기 전에 사라져 facet이 깨진다. 따라서 빌더 흐름은 materialize → Slice-1 fold(fold + foldable 제거) → Slice-2 drop(나머지 orphan 제거)이다. 구현은 compute() 끝의 Slice-1 nodes.retain/edges.retain 블록 직후에 별도 주석 블록으로 추가했다(ORPHAN_TELEMETRY_KINDS 필터 → nodes.retain + dangling edge edges.retain). 테스트 tests/graph_orphan_telemetry_dropped.rs가 단일 그래프에서 fold 보존(facet 생성)과 orphan 제거를 동시에 검사하여 이 순서를 잠근다.

데이터는 보존된다 (SSOT)

telemetry 데이터 자체는 observed_event/raw_event(SSOT)에 그대로 남는다. compute()는 이벤트로부터 그래프 노드/엣지만 빌드할 뿐 observed_event를 쓰지 않으므로, 그래프에서 노드를 빼도 명시적으로 보존할 것이 없다. 실측 불변식 테스트 tests/graph_backbone_invariant_real.rs는 실제 OTLP logs fixture(logs_v01.json의 hook_execution_complete·mcp_server_connection orphan log)를 ingest한 뒤, accepted log 수가 observed_event에는 그대로 들어가지만 graph_node의 log_record는 0임을 검증한다.

지연(defer): metric → 세션 facet + metric view

이 슬라이스는 metric facet을 만들지 않는다. metric → session-level facet + metric view는 별도 후속 슬라이스다. metric 데이터는 지금은 observed_event에만 남는다.

안전성 분석 (검증된 무영향 소비자)

  • turn_order 엣지 생성은 이미 이 4종을 제외한다(build.rs의 ordered 필터).
  • episode classifier와 모든 insight extractor는 observed_event를 읽지 그래프 노드를 읽지 않는다 — finding/episode 수는 변하지 않는다(api_findings·episode_*·inferred_edge_counts 테스트 green 확인).
  • 어떤 edge inference rule도 이 node_kind들을 소비하지 않는다.
  • API/MCP/프론트엔드 영향은 cosmetic(telemetry timeline lane이 얇아짐).

영향받은 기존 테스트(의도된 계약 변경)

telemetry 노드의 그래프 존재를 단언하던 기존 테스트들을 Slice 2 계약(SSOT 보존 + 그래프 drop)에 맞게 갱신했다: graph_facet_edges.rs(orphan log/span이 노드로 남는다 → drop된다), graph_build.rs(hook_event 노드 merge-key → 그래프 노드 없음), hook_ingest.rs·otel_ingest.rs·otel_logs_ingest.rs·otel_metrics_ingest.rs (그래프 노드 수 단언 → observed_event SSOT 보존 + 그래프 0개). Slice 1 fold 테스트(graph_telemetry_fold·graph_facet_real)는 변경 없이 통과한다.

운영 주의 — 스키마 마이그레이션 없음, 재빌드 필요

스키마 마이그레이션 없음 — 노드 drop은 빌더 출력만 바꾼다. 기존 dev-DB의 graph 행은 이전(orphan 포함) 형태를 들고 있다. orphan이 빠진 그래프로 재생성하려면 세션을 다시 빌드한다(transcript 재ingest 또는 serve의 OTLP-배치/시작-시 rebuild).

Episode/phase classification 제거 (2026-05-31)

브랜치: episode-phase-removal · 날짜: 2026-05-31 · 트랙: episode-redesign epic. Spec: docs/superpowers/specs/2026-05-31-episode-phase-removal-design.md.

derived Episode 객체와 7-phase 분류 (intake/exploration/diagnosis/action/verification/repair/drift), 이를 소비하던 missing_verification finding extractor, episode DB 테이블, 그리고 GET /v1/sessions/:id/episodes·GET /v1/episodes/:id API endpoint를 모두 제거했다. 코드(src/webui/tests/migrations) 변경은 이미 커밋되어 있고, 이 노트는 그 제거를 사양 문서에 반영한 기록이다.

제거 근거

  • action phase가 신뢰할 수 없었다. read-only 명령(예: ls, cat, git status)이 mutation으로 오분류되어 action으로 잡혔다. 휴리스틱이 "무엇을 실행했는가"를 "무엇을 바꿨는가"와 구분하지 못했다.
  • diagnosis/repair phase가 한 번도 발화하지 않았다. top-level vs nested is_error 경로 버그 때문에 error 신호를 잡지 못해 이 두 phase의 분류 조건이 영영 충족되지 않았다.
  • 데이터 계층이 잘못됐다. 분류는 derived Episode가 아니라 개별 event에 속해야 했다. event 위에 별도 episode 레이어를 쌓는 구조 자체가 누적·겹침 버그의 원인이었다(이전 issue 기록 참조).

무엇이 대체하는가

message view의 activity-run fold가 episode를 대체한다. activity-run은 연속된 행동 이벤트를 시각적으로 접어 보여줄 뿐 어떤 분류(phase)도 요구하지 않는다 — 분류 휴리스틱이 없으므로 오분류·미발화 문제가 원천적으로 발생하지 않는다.

유지되는 것 (제거 대상 아님)

  • telemetry fold + facets (Slice 1–2) — 그대로 유지.
  • verification_run 테이블·객체·/v1/verification-runs* — 그대로 유지.
  • diff_hunk 테이블·객체·file lineage — 그대로 유지.

운영 주의 — migration 0017 (DROP TABLE episode)

migration 0017이 episode 테이블을 DROP한다(직전 최신 migration은 0016). 기존 dev DB(.witmcc.sqlite*)는 witmcc init-db로 재생성해야 한다. episode 데이터는 derived 산출물이라 SSOT(observed_event/raw_event)에서 다시 빌드 가능하므로 잃는 원본은 없다.

★ Event-first 뷰 재설계 — 데이터 모델·뷰 계층 변경 (2026-06-02~04, PR #33)

이 섹션은 메세지/디테일/raw 뷰가 "graph node + facet"에서 "ObservedEvent + correlation 키"로 바뀐 재설계의 정식 기록이자 cross-reference 대상이다. 사양서(02_technical_architecture· 03_data_model·04_api_mcp·01_product_design)는 옛 graph-backed 모델을 서술하므로, 그 문서들에는 이 섹션을 가리키는 callout이 삽입돼 있다.

개념 전환 (한 줄)

세 뷰(메세지·디테일·raw)는 graph를 거치지 않고 ObservedEvent + raw_event + correlation 키(tool_use_id=한 도구 호출, request_id=한 LLM 턴, event_uuid/parent_uuid=스레드)로 직접 그린다. graph(node·edge·facet-fold)는 이제 causal-edge inference + 공개 /graph Pull API/MCP 전용이고 뷰 경로에선 완전히 빠졌다.

용어 (혼동 주의)

  • event = ObservedEvent. 뷰가 다루는 유일한 단위. raw에서 정규화되고 raw 포인터를 보존.
  • raw_event = 동결된 원본(transcript 줄/OTLP/hook). /v1/events/:id/raw.
  • node / entity = backbone event가 승격된 GraphNode (event의 부분집합). 뷰에선 더 이상 안 씀.
  • facet ① (ingest) = observed.rs의 TelemetryFacet/LogFacet/MetricFacet — 한 텔레메트리 관측의 정규화 단면(= 그 event payload의 모양). 유지.
  • facet ③ (graph fold 결과) = build.rs가 owner node의 payload.facets에 접어넣은 것. 뷰에서 제거(graph/insight 경로에만 잔존). ①과 ③은 무관한데 한 단어를 공유 — webui에선 ③을 완전히 삭제했다.
  • correlate = tool_use_id/request_id로 두 event를 잇기(node/facet 아님).
  • beat = message stream에 독립 카드/활동으로 그려지는 event.

변경 5가지

  1. event-first 뷰 — DetailPanel/InsightTab이 node: GraphNodeDto → event: ObservedEventDto; SessionDetailPage가 graph 쿼리/매핑 제거; findings는 event_id로 매칭. 상세: #views-without-graph.
  2. conversation-anchored 초기 window — no-cursor window가 raw가 아니라 렌더되는 event 기준 [limit번째 최신 렌더 event, 최신 렌더 event] 범위. 텔레메트리 버스트로 끝나는 세션의 빈-화면 해결. 상세: #conversation-anchored-window.
