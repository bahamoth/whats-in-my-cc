01Architecture Overview

아키텍처는 로컬에서 실행되는 observation-to-insight pipeline이다. 모든 source layer는 raw evidence store(raw_event)에 원본 그대로 보존되고, normalized event store(ObservedEvent)와 side-tables·signal store를 UI·Pull API·MCP Streamable HTTP가 공유한다. 뷰와 insight 모두 ObservedEvent + correlation 키 컬럼을 직접 읽는다(event-first) — 별도 graph 레이어는 없다.

02Local Runtime Boundary

Process model

단일 로컬 서비스 프로세스가 collector, pipeline, UI server, Pull API server, MCP Streamable HTTP endpoint를 제공한다. 구현 시 분리는 가능하지만 logical boundary는 하나로 정의한다.

Network model

기본은 127.0.0.1 binding이다. LAN 노출은 explicit setting으로만 허용한다.

Storage model

raw evidence, normalized event, side-tables(usage/diff/verification), signal, audit를 단일 SQLite(.wimcc.sqlite, migrations 최신 0022) 안의 logical store로 둔다.

Trust model

사용자가 소유한 로컬 데이터를 대상으로 한다. 외부 client는 read-only consumer다.

OTel-first 설계: OTel Receiver는 optional plugin이 아니다. trace/span identity가 correlation과 cost/latency attribution의 핵심 key이고, OTLP tool_result log는 outcome resolution 체인의 Tier-1이므로 MVP부터 source contract에 포함한다.
File lineage 소스: 별도의 filesystem watcher나 git poller는 없다 — file lineage는 transcript의 toolUseResult에서 session-scoped로 도출한다. Commit SHA는 verification marker로 사용되지 않는다 — verification semantics는 (a) Bash tool_result(test 명령의 stdout/exit), (b) hook PreToolUse/PostToolUse verification command, (c) OTel verification span에서만 도출된다.

04Pipeline Stages

Stage 1 · Capture

transcript live tail + wimcc ingest backfill + OTel collector가 raw source event를 수집하고 raw_event에 원본 그대로 보존한다(source_uri, offset, capture timestamp 부여).

Stage 2 · Redaction Gate

raw_event 저장 전에 rule_pack@v1(11개 규칙)으로 secret 패턴을 마스킹한다 — src/security/redaction/, ingest/otel 경로 모두 scan() 통과. high-entropy 문자열은 flag-only, 결과는 raw_event.redaction_manifest + meta.redaction_summary로 기록. export-side review·경로 redaction은 제공하지 않는다.

Stage 3 · Normalize

source별 parser가 ObservedEvent로 변환한다. correlation 키(tool_use_id/request_id/turn_id/message_id)는 1급 컬럼이다. OTel metrics/logs/traces는 telemetry facet을 가진다.

Stage 4 · Side-tables

usage_facet(토큰·모델), diff_hunk(transcript toolUseResult.structuredPatch), verification_run(test/build/lint 분류 + outcome resolution 체인으로 status 결정)을 추출한다.

Stage 5 · Insight

ingest가 insight 파이프라인을 직접 호출한다. deterministic L1 detector 5종(tool_failure, risky_action, context_bloat, final_state_mismatch, re_read)이 Signal을 생성한다 — evidence_refs 필수, 외부 write 없음.

Stage 6 · Serve

UI, Pull API, MCP Streamable HTTP가 동일 read service를 읽는다. SessionMetrics는 저장하지 않고 조회 시 on-demand 계산한다(count만 — rate scalar 없음). SSE /v1/stream이 WebUI 라이브 갱신을 담당한다.

Outcome resolution 체인 (tool_result / verification status): ① OTLP tool_result log의 success attribute → ② hook post_tool_use exit_code → ③ transcript "Exit code N" 라인 → ③b <tool_use_error> 래퍼 → Failed(Measured; Cancelled는 예외) → ④ Unknown. 어느 tier에서 잡혔는지는 status_provenance(measured/estimated/unknown)로 보존된다. Tier-4 (estimated): looks_like_failure/success 텍스트 패턴 기반 추정 — verification_run 추출 경로에서 command kind가 verification kind(test suite/build/lint/format_check 등)일 때만 적용된다. 일반 tool_result의 outcome resolution은 Tier-1~3b 이후 Unknown으로 종료한다. 또한 disposition(tool_result 하니스 마커 prefix → user_rejected/policy_denied/cancelled/backgrounded)이 잡힌 결과에는 적용하지 않는다(가드).

05Logical Stores

Raw Evidence Store

raw_event — 원본 payload, source identity, offsets. unknown field도 그대로 보존(source-preserving).

Normalized Event Store

ObservedEvent — source_refs, telemetry facet, correlation 키 컬럼(tool_use_id/request_id/turn_id/message_id; request_id 인덱스).

Side-table Store

usage_facet, diff_hunk(Edit만 hunk 생성), verification_run(status_provenance measured/estimated/unknown).

Signal Store

Signal — detector@v1, subkind, summary, facts(JSON), evidence_refs, provenance{detector, version:"L1", rule_pack}.

Audit Store

local access log, retention deletion.

모든 store는 단일 SQLite 파일(.wimcc.sqlite) 안의 logical 분리다. migrations 현재 head는 0022다. Detector manifest는 DB store가 아니다 — 코드에 컴파일된 정적 상수(src/insight/manifest.rs)이며 GET /v1/detectors와 MCP list_detectors로 노출된다.

06Correlation Strategy

correlation 키는 ObservedEvent의 1급 컬럼이며, 뷰·디테일 패널·detector가 조회 시 직접 join/필터에 사용한다.

07OTel Integration Details

OTel data는 단순 metric dashboard용이 아니라 correlation identity와 outcome/quality signal을 제공한다.

Metrics

token, cost, cache, active time, model usage, tool counts. metric_sample 이벤트로 보존, usage/baseline 집계에 사용.

Logs / Events

API request/error, tool result, lifecycle event. Transcript/hook와 cross-reference. OTLP tool_result log는 outcome resolution 체인의 Tier-1.

Traces

span hierarchy, parent-child relation, latency attribution. otel_span 이벤트 — correlation의 backbone.

Resource attributes

service.name, session.id, project, user-local context. 세션/소스 grouping에 사용되고 telemetry.resource로 원본 보존된다. access control에는 사용되지 않는다(인증은 bearer 미들웨어뿐).

08Serving Architecture

Event-first serving: Local UI의 메세지·디테일·raw 뷰는 Normalized Event Store(ObservedEvent) + Raw Evidence Store를 correlation 키(tool_use_id/request_id)로 직접 읽는다. 모든 serving path가 동일하다 — 중간 표현 레이어 없음.

Local UI

React SPA(rust-embed). /sessions 목록, /sessions/:id event-first replay — 대화 스트림, per-event 디테일 패널, Raw 탭, insight strip(provenance 배지), 분석 패널, untagged-Bash 패널. SSE /v1/stream으로 라이브 갱신.

Pull API (read-only GET)

/v1/health(/sources) · /v1/sessions(/:id) · events · turns · diff-hunks · usage · metrics · fingerprint · signals · verification-runs · /v1/verification-runs/:id · /v1/signals/:id · /v1/usage/baseline · /v1/metrics · /v1/detectors · /v1/events/:event_id/raw · /v1/audit · /v1/stream(SSE). 응답은 {meta, data} 래핑.

MCP Streamable HTTP

단일 로컬 endpoint /mcp, read-only 도구 6종: search_sessions · get_file_lineage · get_otel_trace · get_session_turns · get_project_metrics · list_detectors. resources 기능도 제공한다 — resources/list · resources/templates/list · resources/read, resource template 3종: whats-in-my-cc://sessions/{session_id} · whats-in-my-cc://file-lineage/{session_id} · whats-in-my-cc://otel/traces/{trace_id}.

Boundary: serving layer never applies improvements. No CLAUDE.md update, no hook install, no skill generation, no memory write.

10결정 사항과 미제공 범위

  1. OTLP receiver는 서비스 내장이다(/otel/v1/* collector endpoint). 별도 collector dependency는 없다.
  2. raw evidence store encryption-at-rest는 제공하지 않는다(post-MVP).
  3. file snapshot은 transcript structuredPatch hunk만 보존한다. 전체 파일 snapshot은 없다.
