# wimcc 자기개선 지표 적합성 평가 (설계)

**질문 하나에 답한다:** *코딩 에이전트가 자기 워크플로우를 스스로 개선하는 데, wimcc가 내놓는
데이터가 지표 소스로 충분한가?*

산출물은 개선 patch도, 로드맵도 아니라 **증거 기반 평가 보고서**다. "충분하다/부족하다"와,
부족하다면 **어디가 어떤 성질로 부족한지**를 다양한 세션에 걸쳐 잠근다.

## 1. 평가 대상 — 4 영역

코딩 에이전트 워크플로우 개선이 걸리는 네 영역(사용자 정의):

1. **Spec 정합성** — CLAUDE.md/AGENTS.md 같은 이니셜 프롬프트의 비효율·drift
2. **LLM 하네스** — skill / tool_call / mcp / hook / sub_agent 사용의 비효율
3. **코드·테스트** — 구현·테스트 결과로부터의 개선점
4. **모델·비용** — 모델 적정성, 캐시 등 비용 효율

## 2. 채점 rubric — **두 축** (핵심: 판정/추정 금지)

> **철학:** wimcc는 판정하지 않는다. 결정론적으로 명백히 확인되는 지표·스멜은 그대로 계산·노출하되,
> **정량화하기 어려운 판정을 판독기 로직으로 가정·가설·추정에 근거해 만들면 안 된다 — 그러면 전부
> 무너진다.** 판정이 필요하면 그 판정은 **LLM이 하도록 데이터를 제공**하는 것으로 끝낸다.

영역마다 "개선에 필요한 신호"를 가용성만으로 보지 않고 **먼저 성질을 가른다.**

### 축 A — 신호의 성질

- **결정론적 사실 (fact):** 관측에서 객관적으로 확정. tool 호출 발생 여부, exit code, 토큰 수,
  sidechain 묶음, hook blocking 여부, request_id별 model, cache read/write 바이트 등.
- **판정 필요 (judgment):** 가치·규범 평가가 들어감. "이 turn이 비효율인가", "이 CLAUDE.md 지시를
  위반했나", "이 skill을 안 쓴 게 잘못인가", "이 모델이 과한가" 등.

### 축 B — 가용성

- ✅ wimcc 가공 지표/facet/집계로 바로 노출
- 🟡 raw event(payload)에 데이터는 있으나 미가공(직접 파싱 필요)
- ❌ 원자료 자체 부재

### 처방 규칙

| 성질 | 가용성 gap(🟡/❌)일 때 올바른 처방 | 안티패턴 |
|------|-------------------------------|---------|
| **fact** | deterministic facet/집계 추가 | (없음) |
| **judgment** | **evidence 묶음**을 join+노출만. 판정은 LLM. | 점수화/추정 detector — 가설·휴리스틱으로 judgment를 정량화하는 모든 것 |

따라서 평가의 출력엔 "어떤 신호가 부족하다"뿐 아니라 셀마다 **"fact냐 judgment냐, 따라서
deterministic facet인가 evidence-assembly인가"**가 붙는다.

## 3. 표본 — 세션 패널 × 4 영역 grid

단일 세션 편향을 없애기 위해 **다양한 모양의 세션 패널**에 걸쳐 채점한다. 각 (세션, 영역) 셀에서
독립적으로 data-sufficiency를 매긴다.

### 3.1 세션 패널 (~8개, 결정론적 선택)

## 4. 셀당 채점 절차

각 (세션, 영역)에서:

1. **노출 인벤토리** — wimcc가 그 세션·영역에 대해 결정론적으로 내놓는 것을 Pull API + raw payload에서
   목록화.
2. **신호 분해 + 두 축 태깅** — 영역이 요구하는 신호를 나열하고 각각 (fact|judgment) × (✅|🟡|❌).
3. **오도 지표 cross-check** — 가공 지표가 결정론적 원천과 어긋나는지 **객관 대조**(계산값 대 그
   원천의 비교라 판정이 아니라 결정론적). 어긋남이 이 패널에서 **재현되는 패턴인지** 단발인지 판별.

> 채점은 **데이터의 존재·형태**만 본다. "이 세션이 비효율인가" 같은 judgment를 채점자가 내리지
> 않는다(§2 철학 위반). 채점자는 "그 judgment를 LLM이 내릴 evidence가 조립돼 있나"만 본다.

## 5. 선행 조건 — corpus 재ingest

현 `.wimcc.sqlite`는 **Jun 5자 stale**: graph/judge 테이블 잔존, migration 0019~0022 미적용. exit code
파싱·`status_provenance` 등 measured-coverage가 현 코드와 다르게 들어가 있어 평가가 옛 데이터를 보게
된다. 따라서 **현 스키마(0022)로 재ingest**가 평가 전제(step 0).

## 6. 집계 + verdict

- **data-sufficiency 매트릭스** — 영역 × 세션, 셀마다 (fact|judgment) × (✅|🟡|❌).
- **충분/부족 verdict** — 영역별로 "현 wimcc 데이터만으로 LLM이 개선점을 도출할 수 있나"에 답.
- **broadly-holds vs single-case 플래그** — Real-data anchoring 원칙(표본 수 명시) 준수. N/8 세션에서
  재현된 발견만 일반화.
- **gap 목록** — 각 gap에 (fact→facet | judgment→evidence-assembly) 처방 성질을 부착. (구체 구현은
  본 평가의 범위 밖 — 후속 작업의 입력.)

## 7. 실행 방식 (plan 단계에서 확정 — 옵션)

grid는 (세션 × 영역)의 독립 셀이라 fan-out 가능.

- **(a) 순차 직접** — 메인 세션에서 셀을 순서대로 채점. 토큰 적고 느림.
- **(b) multi-agent workflow fan-out** — 병렬 분석 에이전트. **별도 opt-in 필요**.

권고: ~8 × 4 = 32 셀. opt-in 전까지 (a)로 1~2 세션 파일럿해 rubric을 검증한 뒤 확장.

## 8. 성공 기준

- 8개 세션 패널 전부에 4 영역 매트릭스가 (fact|judgment) × (✅|🟡|❌)로 채워졌다.
- 영역별 충분/부족 verdict가 났다.
- 모든 일반화 statement에 표본 수가 붙어 있다(단일 사례 일반화 0건).
- 각 gap에 fact/judgment 처방 성질이 부착됐다.
